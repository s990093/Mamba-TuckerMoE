📋 為什麼？
────────────────────────────────────────────────────────────────────────────────
你說 cot_format_fsm.py 和 cot_middleware.py 兩個新模組導致生成品質下降。
我已建立了獨立的診斷腳本，不污染任何其他代碼。

🎯 立即運行（5 分鐘）
────────────────────────────────────────────────────────────────────────────────
1. 驗證 CoT 組件本身：

   python diagnose_cot.py --test all

   預期看到：✓ All tests passed

2. 驗證實際推理（"who are you?" 測試）：

   python validate_cot_simple.py --max-tokens 150 --temp 0.7

   預期看到在最後：
   ✓ CoT separation working: both reasoning and final answer present

3. 查看詳細結果：
   - [REASONING BLOCK] — 是否有內容？
   - [FINAL ANSWER] — 是否有內容？
   - [QUALITY CHECK] — 是否都是 ✓？


✅ 如果都通過：
────────────────────────────────────────────────────────────────────────────────
組件本身工作正常。問題可能在：
  1. UI/API 層未正確呈現分離的推理/答案
  2. 系統提示或 prompt 格式問題
  3. 模型版本/權重不匹配

建議：
  - 檢查你的上游 chat_demo.py / server.py 是否使用了新的中間件
  - 驗證它們是否正確解析 CotStreamSplitter 的輸出
  - 比較新 vs 舊版本的 UI 行為


❌ 如果有失敗：
────────────────────────────────────────────────────────────────────────────────
常見症狀及修復：

  問題：沒有推理塊，只有最終答案
  ├─ 檢查：validate_cot_simple.py 的 RAW OUTPUT 是否包含 <think> 標籤？
  └─ 修復：見 DIAGNOSE_QUICK_START.md "症狀 3"

  問題：模型卡在思考，沒有 </think> 或 <final>
  ├─ 檢查：MIDDLEWARE STATE 中 think_tokens 是否 >= reasoning_budget？
  └─ 修復：增加 close_bias_value/close_bias_max，見 DIAGNOSE_QUICK_START.md

  問題：分流器卡在 "between" 模式
  ├─ 檢查：是否達到了 reasoning_budget？
  └─ 修復：增加 close_bias_max 到 24-32

  └─ 單元測試 cot_format_fsm.py 和 cot_middleware.py
