## 8 推論優化（Inference Stack）

### 8.1 Prefill vs Decode 的雙路徑

推論階段依 token 數分成兩條自然路徑：當模型尚在建立上下文時走 prefill；進入逐 token 生成後走 decode。兩者的差異不只在計算量，也在於可否把歷史資訊壓縮成固定狀態。

| 路徑        | 觸發條件                        | 計算                                                       |
| ----------- | ------------------------------- | ---------------------------------------------------------- |
| **Prefill** | 初次輸入長度 $N_\text{pf}>1$    | 平行掃描的 Mamba 狀態建立 + 完整 causal attention          |
| **Decode**  | 每步產生 1 個 token、需 `cache` | 純遞迴單步 $h_t = e^{\Delta A}h_{t-1}+u_t$、週期性 KV 追加 |

在本研究的部署環境中，decode 之所以特別值得優化，是因為單 token 計算本身很小，真正昂貴的常是每層反覆啟動小型算子的控制成本。因此推論端採取圖級融合，把每一層 decode 所需的小操作盡量合併，藉此減少裝置端的提交與排程開銷。對 Apple Silicon 而言，這類融合通常比單純追求更高 FLOPs 更重要。

### 8.2 為何圖級融合在此架構下特別有效（數學說明）

以每一步 decode 的 FLOPs 成本為 $F_\text{compute}$、每層啟動的 command buffer overhead 為 $C_\text{overhead}$。未融合版本每一步 decode 的 wall-clock 為

$$
T_\text{uncompiled} \;=\; L_\text{total}\cdot(F_\text{compute}/B_\text{peak} + C_\text{overhead}),
$$

其中 $B_\text{peak}$ 為硬體峰值吞吐、$L_\text{total}=30$ 為總層數。在 $L=1$ 的 decode 場景，$F_\text{compute}$ 很小，使 $C_\text{overhead}$ 反而成為主導項；30 層的累計啟動成本可輕易超過單 token 的實際算術成本。若把每層原本的 $k$ 個小算子融合為 1 個較大的圖級算子，則每層的 overhead 由 $k\cdot C_\text{overhead}$ 下降為近似單次的 $C_\text{overhead}$，總 wall-clock 可近似寫為

$$
T_\text{compiled} \;\approx\; L_\text{total}\cdot(F_\text{compute}/B_\text{peak} + C_\text{overhead}) \cdot (1/k).
$$

在典型配置 $k\approx 5\sim 8$ 下，decode wall-clock 可因此獲得數倍加速。這個分析也再次說明了 Hybrid 架構的一個部署優勢：當大部分層都由固定狀態的 Mamba 組成時，每層單步計算變得更短，於是圖級融合對降低控制開銷就更有價值。

| Decode $N_\text{dec}$ | $T_\text{slot}$ | Transformer KV (MiB) | Mamba State (MiB) | Total (MiB) |   KV 佔比 |
| --------------------: | --------------: | -------------------: | ----------------: | ----------: | --------: |
|                     1 |             265 |                 4.66 |      8.68 (const) |       13.34 |     34.9% |

**核心觀察**：第一，Mamba 側的解碼狀態三元組（$h$、prev-input、angle-sum）**與序列長度無關**，24 層加總僅約 8.7 MiB 且對 $D$ 永遠恆定；第二，Transformer 側的 KV 確實 $\propto T_\text{slot}$，但因為每 5 層才 1 層 Transformer，乘上 $L_\text{macro}=6$ 而不是總層數 30，整體比全 Transformer 架構省約 5 倍 KV 記憶體；第三，對比 $D=8192$ 下純 Transformer 等價架構需要 $30\cdot 24.77 \approx 743$ MiB，**Hybrid 節省約 80% KV 記憶體**。

### 8.4 Apple MLX TPU-Like 推論優化（StaticDecoder + Metal Fusion）

#### 8.4.0 TPU vs GPU：兩種推論執行模式的根本差異

理解本節優化策略的前提，是釐清 **TPU-like 靜態執行**與傳統 **GPU 動態執行**的本質差異。

傳統 GPU（包括 NVIDIA CUDA）採用**動態執行模式**（eager execution）：Python 前端逐算子呼叫，每個操作即時提交一次 GPU kernel launch，CPU 與 GPU 頻繁交替控制。這種模式靈活但高頻寬互動所帶來的控制開銷，在單 token decode 的低 FLOPs 場景下佔比極高。

**TPU**（Tensor Processing Unit，Google 設計的張量專用加速器）則採用**靜態計算圖（Static Computation Graph）模式**：整個前向計算被預先編譯為一張固定計算圖，推論時由硬體以固定流程執行，CPU 只需提交一次圖執行請求，中間不再介入。這消除了細粒度 kernel launch 開銷，使 TPU 在 batch decode 場景下的控制面效率遠優於 GPU。

Apple Silicon 的 GPU 架構（透過 Metal 與 MLX 框架）提供了**圖級靜態編譯能力**（`mx.compile`），允許將多個算子融合為單一 Metal kernel，實現類似 TPU 的靜態執行行為。本節所述的優化即是在 Apple Silicon 上最大限度地引入 TPU-style 靜態圖執行，同時保留 GPU 靈活性（運行時常數注入、量化推論）。

**GPT 類模型單 token decode 的計算特徵分析：** 設模型參數量為 $P$、層數為 $L$、隱藏維度為 $d$。單 token decode 的浮點運算量為 $\mathcal{O}(2Pd)$，而每層的 kernel launch 次數為 $\mathcal{O}(L \cdot k)$（$k$ 為每層算子數）。當 FLOPs 很小（如 $P = 417\text{M}, d = 768$），控制開銷 $T_\text{ctrl} \propto L \cdot k$ 與計算時間 $T_\text{compute}$ 的比值顯著升高——這正是 TPU-like 靜態圖對小批次 decode 效益最大的場景。

#### 8.4.1 問題根源：分散的 Kernel Launch

在 eager（未編譯）模式下，每一個 token decode 步需要完成的計算被分解為**數十個獨立的 Metal command buffer 提交**——每個 element-wise 操作、norm、einsum 各自對應一次 GPU dispatch。以 30 層、每層估計 ~50 次提交為例，一個 token 的 wall-clock 有相當大比例消耗在 CPU–GPU 協調上，而非實際算術。這在 Apple Silicon 統一記憶體架構上尤其明顯：當計算量很小（單 token decode 的 FLOPs 極低），控制開銷的比重反而超過算術開銷。

在 Apple MLX（m2 pro bf16）上量測：

| 模式 | 每 token 大約 dispatch 次數 | Decode 吞吐 |
|:---|---:|---:|
| Eager（逐算子執行） | ~1,500 次 | ~35 tok/s |
| 按 block 編譯（30 個子圖） | ~30 次 | ~47 tok/s |
| **StaticDecoder（單一全圖）** | **1 次** | **~98–101 tok/s** |
| + Metal Fuse + q8 quant | 1 次 + 2 custom kernels | **~135–144 tok/s** |

#### 8.4.2 靜態解碼器：全圖單次編譯（Static Decoder）

本研究設計了一個 TPU-style 靜態解碼器，將每個 decode step 所需的全部計算——詞嵌入、24 個 Mamba Block、6 個 GQA Transformer Block、語言模型 head、採樣器、in-graph 重複懲罰更新——編譯為**一張靜態計算圖**，以單次 dispatch 執行。

**靜態 KV 快取（Static KV Buffer）。** 實現全圖單次編譯的前提條件是所有張量形狀在編譯時已確定。本研究採用預先分配的固定形狀 KV buffer，每 token 的寫入以原地切片更新（in-place slice update）在計算圖內完成：

$$
K_\text{cache}[\ldots, t, \ldots] \;\leftarrow\; k_\text{new}
$$

此設計消除了執行期的動態 buffer resize，令編譯器能對整個 30 層計算圖進行一次完整的靜態追蹤（tracing），每 token decode 僅需一次 GPU dispatch。

**非同步流水線（Async Pipelining）。** 每次計算圖提交後立即以非同步方式送入 GPU 執行佇列，CPU 主執行緒在 GPU 執行當前 token 的同時進行前一 token 的 detokenize 與串流輸出，實現 GPU 與 CPU 的時間重疊（overlap），進一步隱藏 Python 端的後處理延遲。

**Token 展開（Token Unrolling）。** 在同一張靜態計算圖內部，將 $u$ 個連續 token 的完整 decode 鏈（embed → 30-block forward → sample → re-embed）串接為單一計算圖。相較於逐 token 提交，此設計將 $u$ 次 dispatch 開銷壓縮為 1 次，當 $u = 4$ 時可進一步降低控制面延遲約 20\%。

**常數提升（Constant Hoisting）。** 每個 Mamba block 中由固定權重衍生的常數量——包括旋轉角頻率 $\theta$、bias 項 $b_B, b_C$、D-skip 展開 $D_\text{expand}$——在初始化階段一次性計算並固化，避免在每次 token decode 時於計算圖中反覆執行等冪的指數運算。此預計算不影響數值結果，但可減少計算圖的節點數量，降低編譯追蹤成本。

#### 8.4.3 Metal 融合 Kernel（Block 以下的細粒度融合）

在 `mx.compile` 的圖層級之下，以 Apple Metal Shading Language 編寫兩個自訂 kernel，融合在 block 邊界之下無法被 `mx.compile` 自動合併的操作：

**① SSM 內鏈融合 Kernel（SSM Chain Fusion）**

每個 Mamba block 在單 token decode 時，從 RoPE 角度計算、B/C 矩陣旋轉、input signal einsum、$\lambda$/$\Delta$/$A$ 三元混合，到狀態遞迴 $h_t = \bar{A}_t h_{t-1} + u_t$ 再到輸出 einsum，共涉及約 **20 個細粒度 kernel 啟動**。本研究設計了一個自訂 Metal kernel，將上述計算鏈壓縮為**單次 kernel launch**。

其核心 grid 佈局為 $(N, P, H)$ 個執行緒，每個 threadgroup 對應一對 $(p, h)$ 維度，在 threadgroup 共享記憶體中完成 $y[h,p,\cdot]$ 的 einsum reduction；所有中間結果（旋轉角度的正弦/餘弦、旋轉後的 $B$/$C$ 矩陣、混合後的 input signal）均保留在片上共享記憶體，不回寫外部 DRAM。此設計使 SSM 內鏈成為 compute-bound 而非 memory-bound 操作，並已通過與原始逐算子路徑的逐 token 數值等價驗證。

可選的 **norm-fold** 擴充：將 RMS normalization 的規約運算複製至同一 kernel 內部執行，避免額外的 2 次正規化 + 2 次偏置加法 kernel 啟動，進一步縮減 dispatch 計數。

**② TuckerMoE 路由鏈融合 Kernel（Routing Chain Fusion）**

TuckerMoE 的路由決策鏈——縮放 tanh 正規化、softmax 機率計算、top-$k$ 專家選取、加權混合核心張量 $G_w = \sum_{e} w_e \mathcal{G}_e$——共 **5 個操作**，在每個 MoE 模組每 token 均需執行。本研究設計了第二個自訂 Metal kernel，將整條路由鏈壓縮為單次 kernel launch；後續的核心張量收縮 $x_\text{core} = x_\text{shared} \cdot G_w$ 保留在框架內建的最佳化矩陣乘法路徑（量測顯示手寫收縮 kernel 在此尺寸下較慢）。

此外，第三個輕量 kernel 將正規化閘控運算 $\operatorname{RMSNorm}(y) \odot \operatorname{SiLU}(z)$ 合併為單次 launch（原需 2 次）。

**選擇性 8-bit 量化（Selective Quantization）**

TuckerMoE 的記憶體頻寬瓶頸集中在共享因子矩陣 $U_\text{in}$ 與 $U_\text{out}$，這兩組因子是每 token decode 時的主要 DRAM 流量來源。本研究對全部 66 個 TuckerMoE 模組的 $U_\text{in}^{\top}$/$U_\text{out}^{\top}$ 施加 8-bit 群組量化（group size = 64），而路由 gemv、核心混合計算、SSM 離散化 dt/$A$/$\lambda$ 尾段（精度敏感路徑）、全連接投影與注意力模組保持 bf16——此為**選擇性量化**策略：集中壓縮帶寬主力，同時保護數值精度敏感的計算路徑。

各優化層次的累積效益（M2 Pro, bf16/q8）：

| 優化層次 | 新增技術 | Decode tok/s |
|:---|:---|---:|
| Block-compile（原始） | 30 子圖編譯 | ~47 |
| StaticDecoder（full graph） | 1 次 dispatch | ~62 |
| + metal\_fuse（SSM + Tucker GW） | custom Metal kernel | ~98–101 |
| + selective q8（MoE U 因子） | 8-bit $U_\text{in}$/$U_\text{out}$ | ~131–144 |
| + norm\_fold | RMS 融入 SSM kernel | ~135–144 |

#### 8.4.4 統一記憶體與 Zero-Copy 特性

Apple Silicon 的 CPU、GPU、ANE 共享同一塊統一記憶體池。MLX 在此架構上實現**真正的 zero-copy**：模型權重、KV cache、SSM 狀態、中間 activation 均在同一段 DRAM 中，GPU 讀取時無須任何 CPU→GPU memcpy，因此 decode 的記憶體頻寬完全用於計算所需的 weight read，而非傳輸開銷（圖 poster "60→1 reads, Zero Copy"）。

### 8.5 多策略推測 Jacobi 解碼（Multi-Strategy Speculative Jacobi Decoding）

Speculative Jacobi Decoding（SJD）是一種**不改變輸出分佈**的加速解碼方法：每一輪用一次 $K$-token parallel forward（「verify forward」）驗證 $K-1$ 個草稿猜測，並以貪婪 Jacobi 接受準則接受最長正確前綴，再以該前綴的末端狀態繼續下一輪——在不改變 argmax greedy 輸出的前提下，每輪可能發出 1 到 $K$ 個 token，期望吞吐取決於平均接受序列長度（ARL）。

#### 8.5.1 Jacobi 接受準則

設前一輪確認的末端 token 為 $t_0$，本輪草稿猜測序列為 $[g_1, g_2, \ldots, g_{K-1}]$。Verify forward 以 $[t_0, g_1, \ldots, g_{K-1}]$ 作為批次輸入（一次 $K$-token forward），並從 logits 取 argmax 得預測序列 $[p_0, p_1, \ldots, p_{K-1}]$。接受規則為：

$$
\text{接受} = [p_0],\quad \text{若}\; p_0 = g_1 \;\text{則繼續追加}\; p_1 \;(\text{若}\; p_1 = g_2 \;\text{則再追加 }\ldots)
$$

即從左到右掃描，一旦預測與猜測不符即截斷。接受長度 $m \in [1, K]$，每輪發出 $m$ 個 token。由於 $p_0$ 永遠被接受（不受猜測影響），ARL 的下界為 1；猜測越準確，ARL 越高，wall-clock 加速比越接近 ARL。

**正確性保證**：貪婪 Jacobi 發出的每個 token 均與純自迴歸 argmax 流一致，只要 verify 路徑（`chunk_parallel_scan`, $L>1$）與 AR decode 路徑（single-step recurrence, $L=1$）在數值上等價。在 float32 下兩路徑 bit-exact；在 bf16 下因舍入雜訊偶爾出現微小分歧（稱為 bf16 divergence window），但不影響整體正確性判斷（§9.11）。

#### 8.5.2 三來源混合草稿系統（Three-Source Hybrid Draft System）

為最大化每輪 Jacobi 驗證的猜測命中率，本研究設計了三個互補的草稿來源，其優先順序依序遞減，並在每輪以混合策略填充猜測序列 $[g_1, \dots, g_{K-1}]$。

**來源一：運行時 N-gram 快取（Runtime N-gram Cache）。** 在生成過程中，從已確認的 token 序列（prompt 加所有已接受 token）即時維護一個 LRU $n$-gram 字典，$n=3$，每個 $(n-1)$-gram key 保留最近最常出現（Most-Recently-Used）的若干個後繼 token。每輪 Jacobi 以當前 token $t_0$ 與前綴上下文查詢此字典，取命中的 MRU 後繼填入猜測位置，再以新猜測更新 context 後繼續填入下一個位置，構成鏈式延伸。此 cache 從空白狀態開始，在生成過程中自動積累，不依賴任何預訓練或外部資料。其優勢在於能夠捕捉當前生成片段的短距局部重複模式。

**來源二：後綴檢索器（Suffix Retriever）。** 維護一個包含完整生成歷史的 token 序列，對每個新位置查詢最長後綴匹配（longest suffix match），將匹配段落的後續 token 作為草稿猜測。後綴檢索器的命中率在具有重複結構的長序列（如思維鏈推理的固定格式段落、程式碼模板）上顯著高於純 N-gram，因為它利用的是完整歷史中任意位置的模式，而非固定長度的短 gram。

**來源三：相位感知 CoT 靜態快取（Phase-Aware CoT Cache）。** 離線從訓練 CoT 資料集中萃取 `<think>` 推理階段與 `<final>` 答案階段各自的高頻 N-gram 分佈，形成兩個階段專屬的靜態快取。推論時，相位追蹤器（phase tracker）以偵測 `</think>` 特殊 token 的出現為切換訊號，在兩個快取之間自動切換；各階段的靜態快取提供特定於 CoT 格式的高命中率猜測，不需要任何輔助模型（draft model）。

**混合策略與優先順序。** 每輪猜測序列由上述三個來源按以下優先順序填充：相位感知 CoT 快取命中 $\succ$ 後綴檢索器命中 $\succ$ N-gram 快取命中 $\succ$ 保留種子（前一輪最後一個接受的 token）。三個來源互補而非互斥，其各自的優勢分別對應不同的序列特徵：CoT 快取覆蓋固定格式段落、後綴檢索器覆蓋長距重複模式、N-gram 快取覆蓋短距局部重複，聯合使用可在多種生成情境下維持穩定的高 ARL。

#### 8.5.3 Jacobi 接受準則的嚴格數學分析

**Theorem（貪婪 Jacobi 正確性）。** 設 $f_\theta$ 為固定的 autoregressive 模型，$p_0 = \arg\max_v f_\theta(x_{\le t_0})_v$ 為從上一確認 token $t_0$ 出發的 greedy next-token。在一次 Jacobi 輪中，以 $[t_0, g_1, \dots, g_{K-1}]$ 作為 K-token verify input，logits 的 argmax 序列記為 $[p_0, p_1, \dots, p_{K-1}]$。則以下 $m$ 個 token 被接受：

$$m = \max\bigl\{j \in \{1,\dots,K\} : p_{i-1} = g_i \;\forall i < j\bigr\} \cup \{1\}$$

**Claim：** 被接受的 token 序列 $[p_0, p_1, \dots, p_{m-1}]$ 與對應的逐步 AR greedy 序列完全一致。

**Proof（歸納）。** $p_0$ 始終被接受且等同於 AR 的第一個 token，此為 base case。若 $p_0 = g_1$，則 verify 在位置 1 的輸入前綴 $[t_0, p_0] = [t_0, g_1]$ 與 AR 逐步前綴相同，因此 $p_1 = \arg\max_v f_\theta(x_{\le t_0+1})_v$ 即為 AR 的第二個 token；依此歸納至 $j = m$。$\square$

此定理確保 SJD 輸出與純 AR greedy 的逐 token 一致性，在 fp32 下 bit-exact，bf16 下因舍入雜訊偶爾在 logit margin 極小時發生分歧（稱為 **bf16 divergence window**），但不影響整體結果的統計等價性。

**Wall-clock 加速比的理論上界。** 設每次 verify forward 的計算成本等同 $K$ 步 AR decode 的成本（因為 verify 處理 K 個 token），每輪 Jacobi 發出 $m$ 個 token，則每輪的 wall-clock 等效 AR 步數為 $K$，發出 token 數為 $m$。因此端對端加速比為

$$\text{Speedup} = \frac{m_\text{avg}}{K_\text{eff}} \cdot \frac{T_\text{AR}}{T_\text{verify}/K}$$

其中 $T_\text{verify}$ 為 verify forward 時間，$T_\text{AR}$ 為單步 AR 時間。當 verify overhead 較小（$T_\text{verify} \approx K \cdot T_\text{AR}$）且猜測命中率高（$m_\text{avg} \to K$），加速比趨近 ARL（Average Run Length）。實測在 $K=16$ 下 ARL $\approx 5.92$，但受 verify overhead 制約，實際加速比為 **3.12×**（2048 tok cold）。

#### 8.5.4 No-Replay State 更新（關鍵效率設計）

Verify forward 以批次維度 $(B_\text{tree}, K)$ 一次前向，並**同步記錄每個 token 位置的中間 Mamba 狀態快照**，即對所有位置 $j \in \{0,\dots,K-1\}$ 均保存

$$\text{payload}_j = \bigl(h^{(j)}, \text{prev\_input}^{(j)}, \text{angles\_cum}^{(j)}\bigr)$$

接受長度 $m$ 確定後，直接從 payload 取出位置 $m-1$ 的狀態 $\text{payload}_{m-1}$ 作為下一輪起點，完全省去傳統方法需要「replay forward $m$ 步以恢復正確狀態」的額外計算。此設計的計算節省為每輪最多 $m-1$ 步 AR forward，在高 ARL 場景（$m \approx 5$）效益顯著。

形式上，No-Replay 的 state 更新可寫為：

$$\text{state}^{(t+m)} = \text{extract}(\text{payload},\; m-1,\; b^*) \qquad b^* = \arg\max_{b} \text{accept\_len}(b)$$

其中 $b^*$ 為 Tree 分支中接受最長的分支索引。

#### 8.5.5 Tree 分支與 Adaptive-K

**Tree 分支（$B_\text{tree} > 1$）。** 每輪同時維護 $B_\text{tree}$ 條獨立猜測序列 $\{[g_1^{(b)}, \dots, g_{K-1}^{(b)}]\}_{b=1}^{B_\text{tree}}$，以不同的 N-gram/CoT 候選 seed 在位置 $g_1$ 分歧，位置 $2,\dots,K-1$ 各自鏈式延伸。Verify forward 以 shape $(B_\text{tree}, K)$ 一次完成所有分支的驗證，選取接受最長者。Tree 分支的計算成本與 $B_\text{tree}$ 線性成長，但 Apple Silicon 統一記憶體架構下 $B_\text{tree} \le 4$ 的 overhead 接近免費（實測 $B_\text{tree}=2$ 對 ARL 有 +0.3～0.5 的邊際提升）。

**Adaptive-K（EWMA 動態調整）。** 以指數加權移動平均追蹤 ARL/K 比率 $r_t$：

$$r_t \;=\; (1-\alpha)\,r_{t-1} \;+\; \alpha \cdot \frac{m_t}{K_t}, \qquad \alpha = 0.3$$

策略：$r_t > 0.55$ 時 $K_t \mathrel{+}= 2$（命中率高，擴大視窗）；$r_t < 0.30$ 時 $K_t \mathrel{-}= 2$（命中率低，收縮視窗），邊界約束在 $[K_\text{min}, K_\text{max}]$。Adaptive-K 在命中率隨序列位置或 CoT 階段顯著波動時，自動適應最佳視窗大小。

#### 8.5.6 系統設計原則與效能總結

本 SJD 系統遵循**完全加法設計原則**（additive design pattern）：整個推測解碼層不修改任何現有模型、推論引擎或權重，僅透過對 `model_verify_forward` 的包裝和獨立的草稿 cache 機制，作為純外掛附加在現有 AR 推論路徑之上，不影響標準 AR 生成路徑的數值正確性。

最終加速比數據見 §9.11（表 T2）：$K=16$ 在 2048 tok cold 設定下達 **3.12×**，Demo 場景（暖快取 $c \approx 2$，312 tok）**3.20×**；ARL 層面 $K=16$ 理論最高可達 5.92×，實際加速比因 verify forward overhead 而打折，但在長序列場景仍提供顯著的 wall-clock 收益，且輸出正確性在 greedy decode 下嚴格保證。
