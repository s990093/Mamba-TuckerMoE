第一段：開場與動機

目標 60 秒 · ~155 字
📽️ 投影片：顯示海報大標題，三個瓶頸圖（Attention / KV Cache / MoE）

各位老師、同學，大家好。

我是資工系的賴弘偉，今天我們要報告的專題叫做 Hybrid Mamba-TuckerMoE for On-Device LLM Inference。中文可以理解成「混合式 Mamba 加 Tucker 分解專家模型，用於裝置端大型語言模型推理」。

現在 AI 很普遍，但大家可能不知道：一個真正具有智能的語言模型，光是把它放進記憶體就動輒需要 10 幾 GB——這已經超過大多數筆電和手機的上限了。所以現在這些 AI 幾乎都得靠雲端伺服器才能跑。

我們這個專題問的問題是：能不能把一個 24 億參數等級的大型語言模型，壓縮到只需要四億多個參數，同時還能在 MacBook 上流暢推理，不需要網路？

答案是可以的。讓我來解釋我們怎麼做到。

▶ 本段關鍵詞解釋

LLM（Large Language Model，大型語言模型）

參數量在十億以上的語言理解與生成模型，如 GPT-4、Llama。需要龐大算力與記憶體，通常只能跑在雲端伺服器。

On-Device Inference（裝置端推理）

不依賴雲端，直接在終端設備（手機、筆電）上執行 AI 推理。好處是離線可用、保護隱私、低延遲；挑戰是記憶體和算力嚴重受限。

🖐️ LLM INFERENCE BOTTLENECKS — 手指順序

  1. 手指海報左上角 ① Attention O(N²)，指向 16K seq → 256× cost 的那個箭頭
  2. 移動到 ② KV Cache O(N)，指向 16K tok = 1.4 GiB 那行紅色文字

要了解我們的貢獻，得先知道為什麼把大型語言模型放到邊緣裝置這麼困難。我們歸納出三個根本性的瓶頸。

第一個是注意力機制的計算複雜度是 O(N²)，也就是說輸入序列長度每增加一倍，計算量就暴增四倍。以 16K token 的長文脈輸入為例，計算成本是 512 token 的整整 256 倍，在邊緣裝置上幾乎不可能負擔。

第二個是KV Cache 的記憶體佔用。KV Cache 是 Transformer 推理的加速機制，但代價是佔大量記憶體。512 個 token 就要 113 MB，到了 16K token 就高達 1.4 GB，等於吃掉裝置 88% 的 RAM，根本沒辦法部署。

第三個，也是最有趣的，是MoE 的權重冗餘與頻寬瓶頸。MoE，全名 Mixture of Experts，中文「混合專家模型」，是讓不同輸入走不同「專家子網路」的架構，理論上很高效。但問題在於每生成一個 token，就要從記憶體重新載入不同的專家權重。我們在 M2 Pro 上實測：載入權重要 4.2 毫秒，但實際計算只要 0.04 毫秒——差了整整 100 倍。整個系統完全被記憶體頻寬卡住，根本不是算力問題。

這三個問題，就是我們這個專題的核心出發點。

▶ 本段關鍵詞解釋

O(N²)（平方計算複雜度）

演算法理論中的符號，代表計算量與輸入長度 N 的平方成正比。N 翻倍→計算量變 4 倍。Transformer Self-Attention 就是 O(N²)，這讓長文脈輸入代價極高。

KV Cache（Key-Value 快取）

Transformer 推理時，把每層計算過的 Key 和 Value 向量暫存起來，避免重複計算。加速效果大但記憶體佔用隨序列長度線性成長 O(N)。

MoE（Mixture of Experts，混合專家模型）

每個 token 僅激活部分「專家子網路」，其餘閒置。理論上以少量計算達到大模型容量。但裝置端問題：每個 token 用不同專家，權重不斷換入換出記憶體，造成頻寬瓶頸。

記憶體頻寬瓶頸（Memory Bandwidth Bound）

速度限制來自「資料搬移速度」而非「計算速度」。類比：廚師（GPU）很快，但食材輸送帶（記憶體頻寬）太慢，廚師一直在等材料。

🖐️ Tucker Decomposition & MoE Computation Flow — 手指順序

① Tucker Decomposition Principle（左圖）

  1. 指向左側大方塊 Dense W_e = 75.5M，強調「這是原始專家的大小」
  2. 指向分解後的三個薄板：U_in（1536×256） · Core_e（32×512×256） · U_out（512×6144）
  3. 指向紅色方框 Per-Expert Compression 75.5M → 7.39M（90.2%↓）
  4. 指向 Core_e 說「只有這個是每個專家獨有的，只需要 32 個數字描述個性」

② MoE Computation Flow（右圖）

  1. 指上半 Standard MoE 區塊，描述 K 個平行 GEMM → 輸出空間加總
  2. 指 output-space sum 那個 Σ 符號，說「這就是頻寬殺手」

  5. 指最右下角對比欄（Complexity / On-device Efficiency），確認加速效果

接下來是我們的解決方案，核心架構叫做 Hybrid Mamba-TuckerMoE，有三個主要的技術貢獻。

第一個貢獻：用 Mamba-3 SSM 取代大部分的 Attention。

Mamba 是近幾年提出的「狀態空間模型」，英文 State Space Model，縮寫 SSM。它跟 Transformer 不同的是，它用一個固定大小的「隱狀態」來壓縮並記憶所有歷史資訊，計算複雜度只有線性的 O(N)，而且不需要 KV Cache。我們採用的是第三版 Mamba-3，加入了更精確的梯形離散化方法，讓隱狀態的數值更穩定。我們的架構把多數層換成 Mamba-3，只在少數關鍵位置保留 GQA Attention，取兩者之長。

第二個貢獻：TuckerMoE，用 Tucker 張量分解壓縮 MoE 的專家權重，並從根本改變計算流程。

先說壓縮的部分。每個 MoE 專家的權重矩陣可以想像成一個巨大的 3D 立方體。Tucker 分解把它拆成三個薄板——U_in、Core_e、U_out——相乘的形式。其中 U_in 和 U_out 是所有專家共用的，只有中間那個 Core_e 是每個專家獨有的，而且它非常小，只需要 32 個數字就能描述這個專家的個性。這樣原本一個專家要 75.5M 個參數，壓縮後只剩 7.39M，壓縮了 90.2%。

但更關鍵的是——壓縮不只減少儲存量，它還從根本改變了計算路徑，這才是解決頻寬瓶頸的關鍵。我們來比較兩種做法：

傳統 Standard MoE 的做法是「在輸出空間混合」。路由器選出 K 個專家之後，每個專家各自對輸入 x 做一次完整的大矩陣乘法，算出自己的輸出，最後再把 K 個輸出加權加總。問題就在這裡——每個專家的矩陣 W_e 有 75.5M 個參數，K 個專家就要從記憶體載入 K × 75.5M 的資料量，完全被頻寬卡死。

TuckerMoE 的做法是「在權重空間先融合，再只算一次」。同樣是 K=2 個專家被路由器選中，但我們不去分別跑兩次大 GEMM。取而代之的是：先把 K 個專家的 Core_e 按路由權重加權混合，得到一個融合後的 Core_blended——這個步驟幾乎不費算力，因為 Core_e 只有 32 個數字。然後，用這一個融合核心搭配共用的 U_in 和 U_out，跑三次很薄的小矩陣乘法就完成了。整個過程 K 個專家合力只需要一套 GEMM，U_in 和 U_out 只從記憶體載入一次。這樣記憶體搬移量從 K × 75.5M 降到遠小於一個專家的量，頻寬瓶頸直接消失。

第三個貢獻：多策略投機式雅可比解碼（Multi-Strategy Speculative Jacobi Decoding）。

一般語言模型是逐字生成，一個一個 token 跑主模型，很慢。我們的方法是：先用多種輕量快取——包括 N-gram Cache 和 SuffixRetriever——快速預測出一排候選 token，然後讓主模型一次前向傳播就並行驗證所有候選，通過的直接接受。實測在 Demo 情境下，主模型每次前向傳播平均可以接受 ARL≈5.92 個 token，最高加速達 3.2 倍。

最後，整套系統跑在 Apple Silicon 的 MLX 框架上，CPU、GPU、ANE 三個處理器共享同一塊記憶體，不需要複製資料，做到 Zero-Copy 推理，prefill 吞吐量約 3,800 tok/s。

▶ 本段關鍵詞解釋（必看！最多技術詞）

SSM / Mamba-3（狀態空間模型）

用固定大小的「隱狀態向量」概括所有歷史資訊，複雜度 O(N)，不需 KV Cache。Mamba-3 加入梯形離散化（Trapezoidal Discretization）讓狀態轉移更穩定，並加入 MIMO（多輸入多輸出）投影。

GQA（Grouped Query Attention，分組查詢注意力）

Attention 的輕量版，多個 Query head 共享同一組 K/V，減少 KV Cache 佔用。Llama-2/3 也採用此技術。

Tucker 張量分解（Tucker Decomposition）

把三維（或更高維）張量分解為「小核心張量 Core × 三個因子矩陣 U_in, U_out, ...」的乘積。類似 SVD 但適用於多維。本專題用它壓縮 MoE 專家矩陣，每個專家從 75.5M → 7.39M（-90.2%）。

GEMM（General Matrix Multiplication，通用矩陣乘法）

深度學習最核心的計算操作。TuckerMoE 把傳統 MoE 的 K 次大 GEMM 縮減為 1 次小 GEMM，是速度提升的關鍵。

Speculative Decoding（投機式解碼）

先用快速但可能不準確的「草稿」預測多個候選，再讓主模型一次驗證。驗證比生成便宜，整體加速。本專題不用小模型，改用 N-gram/SuffixRetriever 快取作草稿來源。

ARL（Average Replacement Length，平均替換長度）

每次主模型一次前向傳播平均接受多少個 token。ARL=1 表示完全沒加速，ARL=5.92 表示等效快了約 5.92 倍（實際扣掉驗證成本，加速比約 3.2×）。

N-gram Cache / SuffixRetriever

兩種無需神經網路的快速預測器。N-gram Cache 記憶詞序列後接什麼詞；SuffixRetriever 從上文找相同後綴，預測接下來的詞。本專題三層策略（N-gram + SuffixRetriever + Runtime N-gram）組合使用。

MLX / Zero-Copy / Apple Silicon

Apple 為 M 系列晶片開發的 ML 框架。CPU/GPU/ANE 共享統一記憶體，不需複製資料（Zero-Copy），大幅降低記憶體搬移開銷。

Prefill vs Decode 吞吐量

Prefill：處理輸入 prompt 的批次階段，可並行，速度快（本專題 ~3,800 tok/s）。Decode：逐 token 生成的自回歸階段，是速度瓶頸（本專題實測 Demo ~56 tok/s）。

📽️ 投影片：切換到 Multi-Stage Training & CoT Loss Design 圖 → 手指向公式 → 指 A 圖（Load Balance bar） → 指 B 圖（Router Logit 曲線）

接下來是訓練設計。我們用三階段漸進：預訓練 PPL 24.6 → SFT PPL 18.3 → 自建 CoT 訓練 PPL 12.1。重點放在第三階段的損失函數設計，大家可以看圖，主要有三個部分：

第一個是這個 1/S_t 加權交叉熵——對每個 token 用五種細粒度的 w 來決定它對訓練的貢獻比重，讓推理步驟的 token 比填充 token 被更嚴格地學習。第二個是 λL_FCP，格式合規損失，確保 CoT 的 think 和 final 標籤格式閉合正確。

第三個就是這邊的 A 圖和 B 圖。大家看 A 圖，αL_lb，Expert Load Balance——加這個損失之前，幾乎所有 token 都湧進同一個專家，其他七個閒置；加了之後，你可以看到每個 bar 的高度趨於均勻，這就是防止 Expert Collapse 的效果。再看 B 圖，βL_Z，Router Logit Stability——這是每個 token 路由到八個專家的機率分布，加了 β 項之後曲線變穩定，不會某個專家的機率暴增。這兩個正則項，才讓 MoE 路由真的在「混合」，而不是假裝混合。

▶ 本段關鍵詞解釋

PPL（Perplexity，困惑度）

語言模型標準評估指標，越低越好。PPL 24.6→18.3→12.1 代表三階段訓練顯著有效。

SFT（Supervised Fine-Tuning）

用人工標注的指令-回應對微調，讓模型從「語言預測」變成「指令遵循」。

CoT Loss 五個 w 權重

w_sc（系統指令）· w_go（目標答案，最重要）· w_fw（推理步驟）· w_pd（填充，最低）· w_ic（輸入複製）。讓模型重視推理品質而非平等對待每個 token。

Expert Load Balance / Router Logit Stability

αL_lb 讓路由均勻分配，βL_Z 讓路由機率穩定。兩者共同防止 Expert Collapse（全部 token 湧進同一專家）。

❓ 教授級提問與建議回答（8 題）

請理解後自然回答，不要死背。展示思考過程比背出完美答案更加分。

▶ Q1. Tucker 分解的 rank 是怎麼決定的？有理論依據嗎？
「老師這個問題我自己也研究了很久。嚴格的理論最優 rank 需要分析權重張量的奇異值分佈，但實務上很難事先知道。我們主要靠消融實驗——r1=4、8、16 都試過，發現 r1=8 在 PPL 和記憶體間取得最佳平衡。這屬於工程調參，未來可以考慮用 AutoML 或 Bayesian 優化來自動搜索最佳 rank。」
▶ Q2. Tucker 分解和 LoRA 有什麼不同？
「LoRA 是對權重的『更新量 ΔW』做低秩近似，常用於高效微調；Tucker 分解是對『原始權重矩陣 W 本身』做低秩分解，用於壓縮推理時的記憶體佔用。另外 Tucker 天然適合三維以上的 MoE 張量結構，LoRA 主要針對二維矩陣。兩者都用了低秩假設，但應用時機和作用對象不一樣。」
▶ Q3. ARL 最高有 5.92，但有時候只有 1.22，差距怎麼解釋？
「ARL 高度依賴輸入文本的重複性和快取狀態。如果輸入有大量重複的詞序列，N-gram Cache 命中率高，ARL 就高。在 cold start（快取是空的）或輸入多樣化的情況下，命中率低，ARL 就接近 1。這也是為什麼我們的表格同時報告了 cold 和 warm 兩個情境，不想讓人誤以為隨時都有 5.92 的效果。」
▶ Q4. Mamba 和 Transformer 各自的優缺點，為什麼要 Hybrid？
「Mamba 優點是 O(N) 複雜度、不需 KV Cache，長序列很高效；缺點是固定大小的隱狀態在需要精確長距離回憶的任務上有時表現不如 Attention。Transformer Attention 擅長精確位置對應，但有 O(N²) 問題。我們的 Hybrid 讓 Mamba 負責大量的順序推理，GQA Attention 只在少數關鍵層補足精確召回能力，實測這個組合比 pure SSM 或 pure Transformer 都更適合長文脈裝置端部署。」
▶ Q5. 你們的模型跟 Llama、GPT 的語言品質比怎麼樣？
「直接比較對我們不公平，因為 Llama-3-70B 的參數量是我們的 160 倍以上。我們的定位是『在記憶體和算力嚴格受限的裝置端，同等效容量模型中的最高效率』。我們的對比基準是同等 on-device 場景的模型，如 TinyLlama-1.1B 和 Phi-2——這些比較才是公平的。語言品質我們用 PPL 和 CoT 推理能力衡量，我們的 Val PPL 12.1 顯示訓練顯著有效。」
▶ Q6. Expert Collapse 問題是怎麼發現的，怎麼解決的？
「我們在訓練初期發現 loss 沒有正常下降，去分析路由器的 softmax 輸出分佈，發現幾乎所有 token 都導到同一個或兩個專家，其他六個閒置。解法是加入 Expert Load Balance Loss，強迫路由器讓每個專家的負載接近均勻；同時加入 Router Logit Stability 正則項，防止某個專家的 logit 爆炸性增長。調完這兩個之後，8 個專家的分佈才趨於平衡，模型也開始正常學習。」
▶ Q7. 有沒有在 MMLU、HellaSwag 等標準 benchmark 上測試？
「我必須誠實說，受限於訓練資源和時間，我們目前的評估集中在 Val PPL、記憶體使用和推理速度三個維度。標準 benchmark 評測是我們非常重要的未來工作，PPL 並不等同於下游任務準確率，這也是為什麼我們定位這個研究為 infrastructure 和 efficiency 研究，而不是聲稱達到語言 SOTA。有了完整 benchmark 結果後，我們的論文可信度會更強。」
▶ Q8. 這個研究未來最有潛力的應用場景是什麼？
「最直接的場景是隱私敏感的邊緣 AI——像醫療問診 App（病患資料不能上雲端）、企業內部知識助理（機密資料保護）、離線翻譯器、或者 IoT 裝置上的語音助手。TuckerMoE 的壓縮讓 2.4B 等效容量的模型放進 16GB 筆電，這是現有量化方案（Llama.cpp）之外的另一條技術路線，而且我們的壓縮不依賴量化，可以和量化疊加使用，未來潛力很大。」

🏗️ 架構

LLM / 大型語言模型

參數 10 億以上的神經網路，能理解並生成語言。GPT-4、Llama 都是 LLM。

Transformer

以 Self-Attention 為核心的架構，現代 LLM 的主流基礎。

SSM / Mamba / Mamba-3

State Space Model，用固定大小隱狀態記憶歷史，O(N) 複雜度。Mamba-3 加入梯形離散化和 MIMO 投影。

GQA（Grouped Query Attention）

Attention 的輕量版，多 Query head 共享一組 KV，縮小 KV Cache。

MoE（Mixture of Experts）

每個 token 只激活部分「專家」網路，以少算力達大容量。

RoPE（旋轉位置編碼）

讓模型理解詞的相對位置，是現代 LLM 的標準位置編碼方法。

SwiGLU / SiLU

激活函數，控制神經元輸出的非線性。SwiGLU 常用於 FFN（前饋層）。

LM Head

語言模型最後一層，把隱向量映射到詞彙機率（本專題詞彙量 32,007）。

🗜️ 壓縮技術

Tucker 張量分解（Tucker Decomposition）⭐ 本專題核心技術

Ledyard R. Tucker（1966）提出的多維陣列低秩分解方法，是 CP 分解的廣義版本，適用於三維以上的張量。

① 直覺理解（比喻）

把一本書（3D 張量）拆成三個東西：
· 薄薄的索引頁（U_in）：把所有輸入維度壓縮成精華
· 極小的「概念核心（Core_e）」：只保留最關鍵的 r₁×r₂×r₃ 個交叉關係
· 薄薄的還原頁（U_out）：把壓縮後的概念還原成輸出維度

大部分的「薄薄索引頁」所有專家共用，只有「概念核心」每個專家不一樣，而且這個核心非常小。

② 數學形式

原始的每個專家權重張量 W_e ∈ ℝ^(d_in × d_out) 被分解為：

W_e ≈ U_in · Core_e · U_outT
  • · U_in：1536 × 256，所有專家共用
  • · Core_e：32 × 512 × 256，每個專家獨有（tiny!）
  • · U_out：512 × 6144，所有專家共用

r₁=32, r₂=512, r₃=256 為 Tucker rank，控制壓縮程度

③ 壓縮率計算

Dense W_e（原始） 75.5M 參數
↓ Tucker 分解後
U_in 共用部分 0.05M（只算一次）
Core_e（每專家獨有） 4.19M
U_out 共用部分 3.15M（只算一次）
Total per expert 7.39M → 節省 90.2%

④ Tucker vs SVD vs LoRA

方法 適用維度 作用對象 MSE @ 82.87%
✅ Tucker ≥3 維 W 本身 0.00135
SVD 2 維 W 本身 0.00247 (+45.3%差)
LoRA 2 維 ΔW 更新量 用於微調，非壓縮

Tucker 在相同壓縮量下精度比 SVD 好 45.3%，因為它保留了三個維度的交叉結構資訊，SVD 只能展平處理。

⑤ TuckerMoE 計算流程：Standard MoE vs TuckerMoE

❌ Standard MoE（舊方式）

  1. Top-K Router 選 K=2 個專家
  2. 專家 1 跑：y₁ = W_e1 · x（75.5M 的大 GEMM）
  3. 專家 2 跑：y₂ = W_e2 · x（再一次 75.5M 大 GEMM）
  4. 在輸出空間加權：y = p₁·y₁ + p₂·y₂

問題：需從 DRAM 載入 K × 75.5M 參數，頻寬爆炸

✅ TuckerMoE（我們的方式）

  1. Top-K Router 選 K=2 個專家（相同）
  2. 在權重空間融合核心：Core_blend = p₁·Core_e1 + p₂·Core_e2（只有 32 個數字！）
  3. 跑一次薄 GEMM：h = U_in · x
  4. 跑一次核心縮並：h' = Core_blend ⊗ h
  5. 還原：y = U_out · h'

結果：U_in、U_out 只載入一次，K 個專家合用一套 GEMM

🔑 關鍵洞察

傳統 MoE 混合的是「計算結果」（output space mixing）；TuckerMoE 混合的是「權重本身」（weight space blending）。混完之後只用一組權重跑一次，記憶體搬移量從 O(K × 75.5M) 降到 O(7.39M)，把頻寬瓶頸轉換為算力瓶頸，正好能被 Apple Silicon 的高 FLOPS 利用。

LoRA（Low-Rank Adaptation）

用低秩矩陣 A×B 近似權重更新量 ΔW，常用於高效微調。與 Tucker 不同：LoRA 作用於 ΔW，Tucker 作用於 W 本身。

量化（Quantization）

把 bf16 浮點壓縮成 int8/int4，降低模型大小和記憶體頻寬。可與 TuckerMoE 疊加使用。

GEMM（矩陣乘法）

深度學習最核心計算。TuckerMoE 把 K 次大 GEMM 縮為 1 次小 GEMM，是加速關鍵。

bf16（bfloat16）

16 位浮點格式，與 fp32 相同的指數位寬，適合 ML 動態範圍，節省一半記憶體。

⚡ 推理加速

Speculative Decoding（投機式解碼）

預測多個候選，主模型一次並行驗證，被接受的 token 等同免費取得。

Jacobi Decoding（雅可比解碼）

把多位置並行解碼，類似數值分析的雅可比迭代法，迭代直到收斂。

ARL（Average Replacement Length）

每次主模型前向傳播平均接受多少 token。ARL=1 無加速，ARL=5.92 約 5.92 倍吞吐量。

N-gram Cache

記憶詞序列後接什麼，快速無神經網路預測候選 token。

SuffixRetriever（後綴檢索）

從上文找相同後綴，預測接下來的詞。

Prefill vs Decode

Prefill：批次處理輸入 prompt，並行快速（~3,800 tok/s）。Decode：逐 token 自回歸生成，是速度瓶頸（~56 tok/s）。

tok/s（Tokens per Second）

推理速度指標，越高越好。56 tok/s 在 on-device 場景屬優秀。

🎓 訓練與評估

PPL（Perplexity，困惑度）

語言模型標準指標，越低越好。本專題：24.6 → 18.3 → 12.1 代表三階段訓練顯著有效。

SFT（Supervised Fine-Tuning）

用人工標注的指令-回應對微調，讓模型從「語言接龍」學會「遵循指令」。

CoT（Chain of Thought，鏈式思考）

讓模型先輸出推理步驟再給答案，提升複雜推理準確率。

Expert Collapse（專家坍塌）

MoE 訓練失敗：路由器全選同一專家，其他閒置。解法：Load Balance Loss。

消融實驗（Ablation Study）

逐一替換元件，驗證每個設計的貢獻。本專題用來比較不同 Tucker rank。

FineWeb-Edu / UltraChat

訓練資料集。FineWeb-Edu：高質量網頁教育文本。UltraChat 200k：多輪對話資料。

OOM（Out of Memory）

記憶體超出硬體上限導致崩潰。Dense MoE E8 在 M2 Pro 上 OOM；TuckerMoE 成功避免。

💻 硬體與系統

Apple Silicon / M2 Pro

Apple 自研 ARM 晶片，CPU/GPU/ANE 共用統一記憶體，非常適合 LLM 推理。

MLX

Apple 為 M 系列晶片開發的 ML 框架，支援 mx.compile 圖優化，Zero-Copy 推理。

Metal（Apple GPU 程式語言）

類似 CUDA 的 Apple GPU 程式語言。本專題用它寫自定義 SSM scan 融合核心。

Zero-Copy

CPU/GPU 共享記憶體，無需複製資料即可互相存取，降低搬移開銷。

ANE（Apple Neural Engine）

Apple Silicon 中的神經網路加速器，專門處理特定矩陣運算。

📐 數學符號快查

O(N²) vs O(N)

大O符號。N²：計算量與 N 的平方成正比（Attention）。O(N)：線性（Mamba）。

W_e ≈ U_in · Core_e · U_out

Tucker 分解公式。每個專家的大矩陣 W_e 被分解為三個小矩陣的乘積。

ARL = K=16 → 5.92

K 是候選 token 數量，ARL 是平均接受數量。K=16 時最佳 ARL 為 5.92。

r1=8（Tucker rank）

Tucker 分解的第一維秩值，控制壓縮程度與表達能力的平衡，實驗最佳為 r1=8。

82.87% 壓縮 = 2.4B → 417M

整體壓縮率計算：(2400-417)/2400 ≈ 82.6%（海報數字 82.87% 含精確實測值）。
