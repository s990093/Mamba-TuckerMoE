02

Apple GPU 兩級本地記憶體模型

Tier 1 — 暫存器檔案
每核心 208 KiB Register File
由 SIMD-group（32 執行緒）獨佔存取，延遲趨近於零。可直接與 simdgroup_matrix（AMX 硬體加速器）對接進行超高吞吐量的矩陣運算。這是最快的記憶體層級，目標是將所有中間計算鎖定於此。
Tier 2 — Threadgroup Memory
每 Threadgroup 32 KiB SRAM
相當於 CUDA Shared Memory，供同一 Threadgroup 內所有執行緒共享。速度遠快於全域記憶體，但具有複雜的 Bank 結構。M3（G15）的 Bank 行為與 M1/M2 截然不同，是效能優化的關鍵戰場。
Global — Device Memory
統一 LPDDR5 — 200 GB/s
CPU/GPU 共享的高頻寬記憶體。BS=1 下整個推論是 Memory-bound，目標是最小化往返次數，所有中間狀態避免回寫至此層。非連續（Gather）存取會破壞 Prefetch，需用 Padding/Swizzling 轉為連續存取。
💡
優化核心原則：Tucker 分解的核心收縮運算（r3 → r2）應完全在 Tier 1 Register File 中完成（透過 simdgroup_matrix），絕不落入 Tier 2 Threadgroup Memory，從而徹底迴避 Bank Conflict 風險與同步開銷。
03

Bank Conflict 成因與消除策略

Threadgroup Memory 由 32 個獨立 Bank 組成，每個 Bank 寬 4 bytes。衝突發生當多個執行緒在同一時脈週期存取同一 Bank 的不同位址，導致硬體序列化處理，最壞情況延遲飆升 32 倍。

❌ 衝突根因：32-way Bank Conflict
r_out = 64 → Stride = 64 × 2B = 128 bytes
Bank ID(t) = ⌊(t × 128) / 4⌋ mod 32 = (t × 32) mod 32 = 0

32 個執行緒全部落入 Bank 0，引發最嚴重的 32-way 序列化。

M1/M2 vs M3 記憶體庫行為差異
存取步幅（Stride） M1/M2 (G13) M3 (G15) 說明
Stride 1（連續） ✓ 無衝突 ✓ 無衝突 最佳存取模式，兩代皆相同
Stride 2（偶數） 衰退 ~50% ✓ 無明顯懲罰 M3 在偶數步幅行為不同
Stride 8/16/24 中度衝突 嚴重懲罰 M3 特有半週期性異常
Stride 32 32-way 最壞衝突 ✓ 異常優異 M3 悖離傳統認知
Coalesced Stores 支援並鼓勵 強烈偏好（Stride 1-4） M3 最關鍵優化點
三種消除策略比較
策略 邏輯形狀 Threadgroup Stride Bank 衝突 實作複雜度
未優化 Baseline [E, r_in, r_out] r_out (e.g. 64) 32-way 極端衝突 極低
離線張量轉置 [E, r_out, r_in] 1（完美連續） 0 衝突 低（需改上游導出）
數學互質填充 Padding ★ [E, r_in, r_out+8] 40（Δpad=8） 0 衝突（M2+M3） 中（修改 MSL 索引）
XOR Swizzling [E, r_in, r_out] 1（邏輯上） 0 衝突 高（位元運算）
✅
本 Kernel 採用 Padding 策略：令 Δpad = 8，Row Stride = 32 + 8 = 40 個 bfloat16 元素（80 bytes）。40 與 32 互質（gcd(40,32) = 8 打破週期），確保 32 個執行緒在 M2/M3 兩代上皆實現零 Bank Conflict 的向量化寫入。
Stride_row = T_K + Δpad = 32 + 8 = 40 elements

Offset_dst(Tidx) = ⌊Tidx / 8⌋ × 40 + (Tidx mod 8) × 4

Kernel 常數定義與資料結構

MSL constants_and_structs.metal 
#include <metal_stdlib>
#include <metal_simdgroup_matrix>   // ① 必要：啟用 AMX / simdgroup_matrix 指令
#include <metal_compute>

using namespace metal;

// ══════════════════════════════════════════════════════════════════
// 硬體與架構常數定義
// ══════════════════════════════════════════════════════════════════

// ② TILE 尺寸：32×32 完美映射至 AMX 的 8×8 區塊（4×4 個子矩陣）
constant uint TILE_M = 32;
constant uint TILE_K = 32;

// ③ Bank Conflict 消除：每行尾端 Padding 8 個 bfloat16（16 Bytes = 2 個 Banks 寬）
//    ROW_STRIDE = 32 + 8 = 40，打破 32-Bank 的 128-byte 週期對齊
//    gcd(40, 32) = 8，確保 32 執行緒映射到 5 個不同 Bank 組
constant uint PAD_BFLOAT = 8;
constant uint ROW_STRIDE = TILE_K + PAD_BFLOAT;  // = 40

// ④ Tucker 分解維度（對應本模型：r3=256, r2=1024）
//    在 JIT 編譯時由 Python 端注入為 hardcoded 常數，降低 branching overhead
constant uint R3 = 256;   // Tucker rank3：降維空間
constant uint R2 = 1024;  // Tucker rank2：專家核心維度

// ══════════════════════════════════════════════════════════════════
// 雙重緩衝結構體（Double Buffering for Software Pipelining）
// ══════════════════════════════════════════════════════════════════

// ⑤ 在 Threadgroup Memory 分配兩個 Stage 的空間
//    Stage 0 給 ALU 計算時，Stage 1 在背景預取下一 Tile
//    ROW_STRIDE（含 Padding）確保零 Bank Conflict
struct ThreadgroupStage {
    bfloat expert_tile[TILE_M][ROW_STRIDE];  // 32×40，包含 Padding
};

// ⑥ 雙重緩衝陣列（兩個 Stage 交替使用）
struct PipelineStages {
    ThreadgroupStage stages[2];
};
① metal_simdgroup_matrix
AMX 硬體加速器入口
此標頭檔暴露 simdgroup_matrix<T, M, N> 型態，其資料分散儲存於 32 個執行緒的隱藏暫存器中，直接對接 Apple AMX 協同處理器（等同 NVIDIA Tensor Cores）。
② TILE_M / TILE_K = 32
AMX 友善的 Tile 尺寸
32×32 Tile 讓每個 SIMD-group 計算恰好 4×4 個 simdgroup_matrix<T, 8, 8> 子區塊，完美填滿 AMX 硬體的計算管線。
③ ROW_STRIDE = 40
Padding 策略核心
每行多 8 個 bfloat16（16 bytes），使實體步幅從 32 變 40。40 與 32 的 gcd = 8，打破週期對齊。32 個執行緒的 bfloat4 寫入完美分散到不同 Bank，M2 和 M3 上皆達零衝突。
⑤⑥ 雙重緩衝
Software Pipelining
ALU 計算 Stage[k] 的同時，DMA 在背景將 Stage[k+1] 從 Device Memory 搬移至另一塊緩衝區，實現計算與記憶體傳輸的完美重疊，模擬 NVIDIA TMA 效果。
05

非同步記憶體複製函式（TMA 等效替代）

🔁
NVIDIA Hopper 的 TMA 允許非同步地將張量切片從 Global → Shared Memory，且無需 ALU 參與。Apple Metal 3 的 simdgroup_async_copy 實現等效功能：整個 SIMD-group 協同發起 DMA 請求，ALU 可同時繼續上一個 Tile 的計算。 注意（M3 差異）：M3/M4 上此指令可能是微碼模擬，對 x_shared 向量（單次讀取）反而建議直接從 Device Memory 載入以避免模擬開銷。
MSL async_load_expert_tile() — 硬體級非同步張量搬移 
// ══════════════════════════════════════════════════════════════════
// 硬體級非同步張量搬移函式
// ══════════════════════════════════════════════════════════════════
// 功能：將 G_experts 的一個 TILE_M × TILE_K 切片從 Device Memory
//       非同步搬移至 Threadgroup Memory，同時使用 Padding 策略防止 Bank Conflict
//
// 參數說明：
//   dst         → Threadgroup Memory 目標指標（含 Padding 的緩衝區）
//   src         → Device Memory 來源（G_experts 的基址 + offset）
//   row_offset  → 目前處理的起始 Row 索引
//   col_offset  → 目前處理的起始 Col 索引（K 維度）
//   ld_src      → Device Memory 中 G_experts 的 Leading Dimension（= R2 = 1024）
//   thread_id   → 當前執行緒在 SIMD-group 內的 ID（0~31）
// ══════════════════════════════════════════════════════════════════
inline void async_load_expert_tile(
    threadgroup bfloat*       dst,          // ① Threadgroup 目標
    const device bfloat*  src,          // ② Device Memory 來源
    uint                        row_offset,
    uint                        col_offset,
    uint                        ld_src,       // = R2 = 1024
    uint                        thread_id     // 0 ~ 31
) {
    // ③ 每個執行緒負責搬移 4 個 bfloat16（= 1 個 bfloat4 向量，8 Bytes）
    //    32 個執行緒 × 8 Bytes = 256 Bytes = 兩條 128-Byte L2 Cache Line
    //    完美 Coalesced：硬體以最大頻寬進行合併存取

    // ④ 計算 Padding-aware 的目標位址偏移：
    //    Offset_dst(T_idx) = ⌊T_idx / 8⌋ × ROW_STRIDE + (T_idx mod 8) × 4
    //    確保 32 個執行緒以 bfloat4 為單位連續寫入，滿足 M3 Coalesced Store 偏好
    #pragma unroll
    for (uint i = 0; i < TILE_M; i += 4) {
        uint local_row = (thread_id / 8) + i;
        uint local_col = (thread_id % 8) * 4;

        // ⑤ Device Memory 來源索引（線性，完美合併讀取）
        uint src_idx = (row_offset + local_row) * ld_src
                     + (col_offset + local_col);

        // ⑥ Threadgroup Memory 目標索引（含 ROW_STRIDE=40 的 Padding 偏移）
        uint dst_idx = local_row * ROW_STRIDE + local_col;

        // ⑦ 核心指令：Metal 3 的 simdgroup_async_copy
        //    整個 SIMD-group 協同發起 DMA 請求，ALU 可繼續運行
        //    等效 NVIDIA TMA：非同步、無 ALU 參與、延遲隱藏
        simdgroup_async_copy(
            (threadgroup bfloat4*)(&dst[dst_idx]),
            (const device bfloat4*)(&src[src_idx]),
            1   // 複製 1 個 bfloat4 向量（8 Bytes）
        );
    }
    // ⑧ 注意：呼叫後需在讀取前執行 simdgroup_barrier(mem_flags::mem_threadgroup)
    //        確保所有非同步寫入徹底完成（記憶體一致性保障）
}
③ 粒度選擇
bfloat4（8 Bytes）向量化
32 個執行緒 × 8 Bytes = 256 Bytes，精確對齊兩條 128-Byte L2 Cache Line。BF16 每元素 2 bytes，bfloat4 = 4 個元素 = 8 bytes，是在 M2/M3 上實現最大頻寬利用率的最小向量化單元。
④ Padding-aware 偏移公式
確保 Coalesced Stores
公式 ⌊T_idx/8⌋ × 40 + (T_idx mod 8) × 4 確保 32 個執行緒以 bfloat4 為單位的寫入是連續的，完全滿足 M3 對 Coalesced Stores 的強烈偏好，同時避免 M2 的 32-Bank 衝突。
⑦ simdgroup_async_copy
Metal TMA 等效指令
允許整個 SIMD-group 協同發起 DMA 請求。因為非同步，GPU ALU 可在等待資料到達時繼續執行上一個 Tile 的 AMX 矩陣乘法，實現計算與記憶體傳輸的完美重疊。

主 Kernel 函式——完整程式碼

MSL fused_latent_moe_gemv — 完整 Kernel（含逐行註解） 
// ══════════════════════════════════════════════════════════════════
// 主 Kernel：Fused Latent MoE GEMV
// 
// 功能：將 Tucker 分解後的 MoE 推論融合為單一 Kernel Dispatch
//       完全消除中間狀態的全域記憶體往返（Round-trips）
//
// 執行網格配置（Grid Dimensions）：
//   x 軸 → ceil(R3 / TILE_M) = ceil(256/32) = 8 個 Threadgroups（負責 Row 分塊）
//   y 軸 → 1（BS=1 單 Token 推論）
//   z 軸 → 激活 Expert 數量（動態路由結果）
//
// 每個 Threadgroup：32 個執行緒（= 1 個 SIMD-group）
//   → 至少需 9 個 Threadgroups/核心（M3 19 核心需總數 ≥ 171）以飽和 AMX 管線
// ══════════════════════════════════════════════════════════════════
[[kernel]] void fused_latent_moe_gemv(
    const device bfloat* x_shared      [[buffer(0)]],  // x_shared ∈ ℝ^{1×R3}，已過 U_in 降維
    const device bfloat* G_experts     [[buffer(1)]],  // G_experts ∈ ℝ^{E×R3×R2}，Tucker Core 張量
    const device uint*   expert_indices [[buffer(2)]],  // 路由結果：激活的 Expert ID 列表
    device       bfloat* out_hidden    [[buffer(3)]],  // 輸出 y_shared ∈ ℝ^{1×R2}

    // ① Metal 內建執行緒定位
    uint3 threadgroup_position_in_grid      [[threadgroup_position_in_grid]],
    uint  thread_position_in_threadgroup    [[thread_position_in_threadgroup]]
) {
    // ══════════════════════════════════════════════════════════════
    // Phase 0：解析動態路由結果
    // ══════════════════════════════════════════════════════════════

    // ② z 軸索引對應到激活的 Expert ID
    //    每個 Expert 對應的 G_experts 切片連續存放
    //    這裡 expert_id 決定了從哪個位址讀取 Core 矩陣
    uint expert_id  = expert_indices[threadgroup_position_in_grid.z];
    uint thread_id  = thread_position_in_threadgroup;

    // ③ 計算該 Expert 的 Core 矩陣在 G_experts 中的基址偏移
    //    佈局：G_experts[expert_id][row][col]，Row-major
    //    基址 = expert_id × R3 × R2（每個 Expert 的 Core 大小）
    const device bfloat* expert_base =
        G_experts + (expert_id * R3 * R2);

    // ④ 此 Threadgroup 負責的 Row 範圍（x 軸分塊）
    uint row_block = threadgroup_position_in_grid.x * TILE_M;

    // ══════════════════════════════════════════════════════════════
    // Phase 1：Threadgroup Memory 宣告（雙重緩衝）
    // ══════════════════════════════════════════════════════════════

    // ⑤ 在 Threadgroup Memory 宣告雙重緩衝區
    //    Stage[0] 和 Stage[1] 交替使用：一個給 AMX 計算，另一個預取下一 Tile
    //    每個 Stage = TILE_M × ROW_STRIDE = 32 × 40 × 2B = 2.5 KB
    //    兩個 Stage 共 5 KB，遠低於 M3 的 32 KB 限制
    threadgroup bfloat stage_0[TILE_M * ROW_STRIDE];  // 第一個緩衝區
    threadgroup bfloat stage_1[TILE_M * ROW_STRIDE];  // 第二個緩衝區（交替使用）

    // 緩衝指標陣列（方便索引切換）
    threadgroup bfloat* stages[2] = {stage_0, stage_1};

    // ══════════════════════════════════════════════════════════════
    // Phase 2：宣告 AMX 累加暫存器
    // ══════════════════════════════════════════════════════════════

    // ⑥ 宣告 float32 累加矩陣（防止 BF16 數值溢出）
    //    4×4 個 simdgroup_matrix<float, 8, 8> = 32×32 的累積矩陣
    //    這些資料實體打散儲存於 32 個執行緒的隱藏 AMX 暫存器中
    //    完全在 Tier 1 Register File 內，零 Threadgroup Memory 往返
    simdgroup_matrix<float, 8, 8> acc[4][4];
    #pragma unroll
    for (int i = 0; i < 4; i++)
        #pragma unroll
        for (int j = 0; j < 4; j++)
            acc[i][j] = make_simdgroup_matrix<float, 8, 8>(0.0f);

    // ══════════════════════════════════════════════════════════════
    // Phase 3：軟體流水線 Prologue（序幕）
    // ══════════════════════════════════════════════════════════════

    // ⑦ 預取 Tile 0 至 Stage 0（流水線啟動）
    async_load_expert_tile(
        stage_0, expert_base,
        row_block, 0,   // Tile 0，K 方向從 0 開始
        R2, thread_id
    );

    // ⑧ 記憶體屏障：確保 Stage 0 的資料完全落入 Threadgroup Memory
    //    必須在讀取任何 Threadgroup 資料前執行
    simdgroup_barrier(mem_flags::mem_threadgroup);
}
07

軟體流水線主迴圈（Double Buffering）

🔄
雙重緩衝原理：AMX 計算 Stage[k] 的同時，非同步 DMA 在背景將 Stage[k+1] 從 Device Memory 搬至另一塊緩衝區。兩者完全重疊，消除記憶體等待延遲。R2/TILE_K = 1024/32 = 32 個 Tiles 需要遍歷。
MSL 軟體流水線主迴圈 + Epilogue 
    // ══════════════════════════════════════════════════════════════
    // Phase 4：軟體流水線 Main Loop
    // ══════════════════════════════════════════════════════════════

    uint num_tiles  = R2 / TILE_K;    // = 1024 / 32 = 32 個 K 方向的 Tile
    uint stage_idx  = 0;              // 當前計算使用的 Stage（0 或 1）

    for (uint k = 0; k < num_tiles; k++) {
        uint next_k         = k + 1;
        uint next_stage_idx = (stage_idx + 1) % 2;  // 在 0 和 1 之間切換

        // ────────────────────────────────────────────────────────
        // 步驟 1：非同步預取下一個 Tile（與下方 AMX 計算完全重疊）
        // ────────────────────────────────────────────────────────
        if (next_k < num_tiles) {
            // ① 在 ALU 計算 Stage[stage_idx] 時
            //    DMA 同時將 Tile[k+1] 搬至 Stage[next_stage_idx]
            //    兩者完全並行：這是雙重緩衝的核心
            async_load_expert_tile(
                stages[next_stage_idx],   // 目標：另一個緩衝區
                expert_base,
                row_block,
                next_k * TILE_K,         // K 方向偏移
                R2, thread_id
            );
        }

        // ────────────────────────────────────────────────────────
        // 步驟 2：載入 x_shared 並廣播至 AMX 暫存器
        // ────────────────────────────────────────────────────────

        // ② M3 優化：x_shared 直接從 Device Memory 載入（Bypassing Threadgroup）
        //    在 M3 上，單次讀取的向量直接從 Device Memory 載入
        //    可避開 simdgroup_async_copy 微碼模擬帶來的額外開銷
        //    將 x_shared 廣播為 simdgroup_matrix（向量提升為矩陣）
        simdgroup_matrix<bfloat, 8, 8> x_mat[4];
        #pragma unroll
        for (int i = 0; i < 4; i++) {
            // 將 x_shared 的一個 8 元素切片廣播填入 8×8 矩陣的所有行
            //（BS=1 下 GEMV → GEMM 的轉換技巧：使所有 Row 相同）
            simdgroup_load(
                x_mat[i],
                x_shared + (k * TILE_K + i * 8),
                0      // stride=0 觸發廣播：將 1×8 向量複製到 8×8 矩陣的每一行
            );
        }

        // ────────────────────────────────────────────────────────
        // 步驟 3：從 Threadgroup Memory 載入 G_experts Tile 至 AMX
        // ────────────────────────────────────────────────────────

        // ③ 使用 ROW_STRIDE=40（含 Padding）作為步長
        //    完全迴避 Bank Conflict，直接進入 AMX 暫存器
        simdgroup_matrix<bfloat, 8, 8> g_mat[4][4];
        #pragma unroll
        for (int i = 0; i < 4; i++) {
            #pragma unroll
            for (int j = 0; j < 4; j++) {
                simdgroup_load(
                    g_mat[i][j],
                    stages[stage_idx] + (i * 8 * ROW_STRIDE) + (j * 8),
                    ROW_STRIDE     // ← 關鍵：使用 40 而非 32，消除 Bank Conflict
                );
            }
        }

        // ────────────────────────────────────────────────────────
        // 步驟 4：AMX 硬體矩陣乘加運算
        // ────────────────────────────────────────────────────────

        // ④ simdgroup_multiply_accumulate：BF16 輸入，FP32 累加（防溢出）
        //    4×4 個 8×8 子矩陣的分塊乘法，完全在 AMX Tier 1 暫存器中完成
        //    每次呼叫等效於硬體 FMMA 指令，吞吐量遠高於 SIMD FMA
        #pragma unroll
        for (int i = 0; i < 4; i++) {
            #pragma unroll
            for (int j = 0; j < 4; j++) {
                // acc[i][j] += x_mat[j] × g_mat[i][j]
                //（融合乘加 FMA：乘法 + 累加在一個 AMX 週期內完成）
                simdgroup_multiply_accumulate(
                    acc[i][j],     // 累加目標（FP32）
                    x_mat[j],      // 左矩陣（BF16，廣播後的 x_shared）
                    g_mat[i][j],   // 右矩陣（BF16，G_experts Tile）
                    acc[i][j]      // 累加器（讀入再寫出）
                );
            }
        }

        // ────────────────────────────────────────────────────────
        // 步驟 5：等待下一個 Tile 的非同步搬移完成
        // ────────────────────────────────────────────────────────

        if (next_k < num_tiles) {
            // ⑤ simdgroup_barrier：強制同步 Threadgroup Memory
            //    確保 Stage[next_stage_idx] 的 DMA 完全完成後才進入下一迭代
            //    配合 mem_flags::mem_threadgroup 保證記憶體一致性
            simdgroup_barrier(mem_flags::mem_threadgroup);
        }

        stage_idx = next_stage_idx;   // ⑥ 切換緩衝區：0→1 或 1→0
    }

    // ══════════════════════════════════════════════════════════════
    // Phase 5：Epilogue（尾聲）——結果寫回
    // ══════════════════════════════════════════════════════════════

    // ⑦ 將 FP32 累加結果向下轉型為 BF16，寫回 Device Memory
    //    simdgroup_store 會自動對齊 M3 最佳的 128-byte 記憶體事務邊界
    //    無需手動計算位址，編譯器自動生成最寬向量寫入指令
    #pragma unroll
    for (int i = 0; i < 4; i++) {
        #pragma unroll
        for (int j = 0; j < 4; j++) {
            uint out_row = row_block + (i * 8);
            uint out_col = j * 8;
            simdgroup_store(
                acc[i][j],
                out_hidden + (out_row * R2 + out_col),
                R2,      // Output leading dimension
                false    // Row-major 輸出
            );
        }
    }
}

延遲 vs. 吞吐量的戰略取捨
❌ 傳統 SIMD FMA 路徑
Global Memory → XOR Swizzle → Threadgroup Memory
→ threadgroup_barrier → ALUs → FMA
往返延遲 + 同步開銷極高

✅ AMX simdgroup_matrix 路徑
Global Memory（對齊讀取）→ AMX Tier 1 Registers
→ simdgroup_multiply_accumulate（全在暫存器）
完全迴避 Tier 2 所有存取開銷
simdgroup_matrix 特性
資料打散於隱藏暫存器
simdgroup_matrix<bfloat, 8, 8> 的 64 個元素實體打散分佈於整個 SIMD-group 的 32 個執行緒的隱藏暫存器中。所有操作須在 Uniform Control-Flow 下執行，否則行為未定義。
simdgroup_load stride=0
廣播向量為矩陣
當 stride 設為 0 時，simdgroup_load 將同一行資料複製到矩陣的所有 8 行，實現 GEMV → GEMM 的轉換。最終累積結果中所有行相同，取任一行即得正確 GEMV 輸出。
FP32 累加器
防止 BF16 精度溢出
輸入矩陣使用 bfloat（BF16），但累加器聲明為 float（FP32）。BF16 只有 7 bits 尾數，長鏈乘加會迅速累積誤差；FP32 累加器確保最終精度，寫回時再轉換。
Occupancy 啟發式
19 核心需 ≥ 171 Threadgroups
要讓 BF16 填滿 AMX 管線，每個物理 GPU 核心需 ≥ 9 個 Threadgroups。19 核 M3 需總 Threadgroups ≥ 171。若維度過小導致 Occupancy 不足，應縮小 Block Size 從 48×48 → 32×32 → 16×16 以增加 Threadgroup 數量。

# ① MLX 會自動根據 input_names / output_names

kernel = mx.fast.metal_kernel(
    name="fused_latent_moe_gemv",

    output_names=["out_hidden"],

    # ③ 注入 JIT 生成的 MSL 源碼字串

    #    避免執行期 branching overhead 和 function_constant 開銷
    source=generate_msl_with_constants(r3=256, r2=1024),

    header="""
#include <metal_simdgroup_matrix>
""",
    ensure_row_contiguous=True,  # 確保張量記憶體連續
    atomic_outputs=False

def tucker_moe_inference(x, G_experts, expert_ids, r3=256, r2=1024):
    """Tucker MoE 單 Token 推論"""

    # ④ 執行網格計算
    #    x 軸：R3 方向分塊，ceil(256/32) = 8
    #    z 軸：激活 Expert 數量（動態路由結果）
    n_experts = expert_ids.shape[0]
    grid = (r3 // 32, 1, n_experts)   # (8, 1, n_experts)
    threadgroup = (32, 1, 1)           # 1 個 SIMD-group = 32 執行緒

    # ⑤ 確保 G_experts 已離線轉置（推論前預處理）
    #    若上游 Triton 以 [E, r_in, r_out] 導出，需在此預先轉置
    output = kernel(
        inputs=[x, G_experts, expert_ids],
        template=[("T", mx.bfloat16)],
        grid=grid,
        threadgroup=threadgroup,
        output_shapes=[(r2,)],
        output_dtypes=[mx.bfloat16],
        verbose=False
    )
    return output[0]

def generate_msl_with_constants(r3: int, r2: int) -> str:
    # ⑥ JIT 注入 hardcoded 常數
    #    在推論前由 Host 根據當前層維度動態生成 MSL 字串
    #    避免執行期根據 buffer 讀取維度（減少 branching）
    return f"""
constant uint R3 = {r3};
constant uint R2 = {r2};
constant uint TILE_M = 32;
constant uint TILE_K = 32;
constant uint PAD_BFLOAT = 8;
constant uint ROW_STRIDE = TILE_K + PAD_BFLOAT;
// ... 後接完整 Kernel 程式碼
"""
⚡
JIT vs. function_constant：Metal 的 function_constant 允許在 Pipeline 建立時指定常數，但仍需執行期 branch 判斷。JIT 直接將數值烤入 MSL 字串，讓編譯器完全展開迴圈（#pragma unroll），暫存器壓力更低，無分支開銷。
1
Python 端：讀取模型配置
從模型 checkpoint 讀取 r3、r2 等維度配置，傳遞給 MSL 生成函式。不同層可能有不同維度。
2
動態生成 MSL 字串
使用 Python f-string 或 Jinja2 模板，將 R3=256、R2=1024 等數值直接嵌入 MSL 代碼，同時可針對不同 Metal 版本（M2/M3）生成不同的優化路徑。
3
MLX 解析並自動補齊簽名
mx.fast.metal_kernel 框架自動根據 input_names 在 MSL 中生成 const device bfloat16_t* G_experts [[buffer(1)]] 等指標宣告，消除繁瑣的介面綁定。

利用 Metal 4 非同步編譯 API 在模型載入階段預先完成 Pipeline State 的建構，避免在即時 Token 生成時引發編譯卡頓（Stuttering）。

// Metal 4 非同步編譯 API
// 在模型載入階段（非推論熱路徑）預先建構 Pipeline State
// 避免首次 Token 生成時的 JIT 編譯卡頓

let device = MTLCreateSystemDefaultDevice()!

// ① 使用 Metal 4 新 API：非同步編譯
let compileOptions = MTLCompileOptions()
compileOptions.optimizationLevel = .performance

// ② 非同步編譯 MSL 原始碼（不阻塞主執行緒）
device.makeLibrary(
    source: mslSourceCode,
    options: compileOptions
) { library, error in
    guard let library = library else { return }

    // ③ 非同步建構 Compute Pipeline State
    let descriptor = MTLComputePipelineDescriptor()
    descriptor.computeFunction = library.makeFunction(
        name: "fused_latent_moe_gemv"
    )
    descriptor.threadGroupSizeIsMultipleOfThreadExecutionWidth = true

    device.makeComputePipelineState(
        descriptor: descriptor,
        options: [],
        completionHandler: { pipeline, reflection, error in
            // ④ 快取 pipeline 供推論使用
            self.cachedPipeline = pipeline
        }
    )
}
