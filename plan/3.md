直接看结论：想突破 3× 并长期受益，我们应该**将核心策略从单路 N-gram 切换为多候选并行验证（Multi-Candidate / Tree Attention）**，并配合 OS 层级的内存与 I/O 优化来补齐底层短板。具体的策略分两部分：

---

## 🧠 算法层面：从 N-gram 转向“多候选 + 树形验证”

我们当前的 N-gram 草稿本质是**单路猜测**，对抗 token 分歧的能力有限，而学术界 2025–2026 的最新范式已经转向了**多候选路径并行预测 + 一次验证**，这正是最适合我们 zero-training 路线且收益最大的算法升级。

### 1. 核心突破口：Jacobi 的多候选升级

雪球 (Snowflake) 在 2026 年 3 月提出的 **SJD-PAC** 与我们的场景高度吻合：

- **主动草稿 (Proactive Drafting)**：不满足于一次生成一个固定序列，而是主动预测未来多步 token 的概率分布。
- **自适应延续 (Adaptive Continuation)**：动态调整要预先计算的 token 数量。
  这恰好可以解决我们目前 **ARL 天花板 ~0.63** 的问题——一条路猜中的概率有限，但如果我们并行预测 top-3 的下一个 token，并从中选出最优路径，可以有效突破 ARL 上限。

### 2. 关键利器：Tree Attention 一次性验证整棵候选树

我们的 `_batch_replay` 已经证明**并行验证**是可行的，而目前最能放大这一优势的技术是 **Tree Attention**：

- 像 **SpecInfer** 和 **EAGLE2** 那样，将多条候选路径构建成一棵 token 树，一次性送入模型进行并行验证。
- 我们的 `compiled_verify_fns[K]` 基础设施可以直接复用——现在一次验证 32 个 token 序列，未来可以变成“一次验证包含 3 条分支、每条深度 8 的候选树”。
- 配合 **Jakiro**（使用 MoE 并行生成多种猜测）或 **Gumiho**（优先验证早期 token 的候选路径），ARL 有望从 20 提升至 24+。

### 3. 新框架参考：SSD 草稿与验证并行化

两个与 SSD（Speculative Speculative Decoding）相关的工作也值得我们关注：

- **Speculative Speculative Decoding**：在**验证进行的同时**，草稿模型就同步猜测验证结果并准备下一轮草稿，实现时间上的双重并行。
- **UniVer**：将多草稿和多步验证统一为 Optimal Transport 问题，提供数学框架支持。

> 注：上面提到的 SSD 是 “Speculative Speculative Decoding” 的缩写，与我们模型中 Mamba-2 的 “Structured State Space Duality” 是不同概念，特此说明，避免混淆。

## 🖥️ OS/底层层面：压榨 M2 Pro 16GB 的极限性能

16GB 统一内存是当前最大硬约束，但通过 macOS 的特定机制和高效 I/O 策略，可以有效缓解瓶颈。

### 1. 精准内存管理：锁定与预算

- **强制 Wired Memory**：对常驻的 KV Cache 或 N-gram 查找表调用 `mlx.core.eval()` 后，从底层将其 pin 在物理内存中，防止系统在内存紧张时将其换出，保证延迟稳定。
- **GPU 内存预算制**：参考 `dmlx` 的多级内存池思想，写死一个“Metal GPU 内存预算”，在超过 14GB 时自动将不活跃的权重或缓存释放，防止因内存爆满而导致的 OOM。
- **代码级防御**：在每次 `_compiled_verify[K]` 调用前，手动调用 `mx.metal.clear_cache()` 或主动触发一次空闲内存回收。

### 2. 高速 I/O：善用 mmap 与 NVMe 交换

- **权重 mmap 零拷贝**：确保模型权重使用 `mlx.core.load("weights.safetensors", mmap=True)`。这使多个进程可共享物理内存，且无需等待全量加载到 RAM 才能推理。
- **SSD 作内存扩展**：我们的 N-gram 查找表、历史缓存甚至可以创建为 memory-mapped file，利用 NVMe SSD 的读写速度作为 RAM 的逻辑扩展。当前 `mlx-flash` 已在做类似工作。

### 3. 极限压榨 Metal 性能

- **自研 Custom Metal Kernels**：虽然编译优化已做到位，但像 N-gram 查找、`carry_draft` 序列填充这类高度定制的操作，直接编写 Metal Shading Language 内核可以极致压榨性能。
- **利用 MPS 后端**：对于部分矩阵运算（如批量 score 计算），尝试通过 PyTorch + MPS 后端调用 Apple Neural Engine，也许能挖掘出额外的并行潜力。

## P0 — Tree Attention + 多候選並行驗證的原理

### 現在我們的瓶頸：單路猜測的賭注太大

目前 +ngram 在 K=32 時的工作方式是一條線性的猜測序列：

```
guess[0] = carry_token
guess[1] = ngram(carry_token)
guess[2] = ngram(guess[0], guess[1])
...
guess[31] = ngram(guess[0..30])
```

這是一條**單路徑草稿**，只要中間某個位置預測錯誤（比如第 5 個 token），從該點之後的所有猜測（第 6～第 31 個 token）全部作廢。在數學 CoT 上，這條路的每一步準確率大概在 80% 左右，所以 32 步全部正確的概率很低（約 0.8³² ≈ 0.07%），我們實際得到的 ARL=22 是靠「前 20 幾個位置連對、後面斷掉」的模式維持的。

**本質問題**：單路猜測把 32 個位置的命運綁在一起，一斷就全斷。

---

### Tree Attention 的核心思路：分岔、驗證、選最長的那條

Tree Attention 不押注一條路，而是讓多個候選路徑**分岔並行**：

1. **擴展猜測樹**：在每一步，不只猜一個 token，而是猜 top-2 或 top-3 的 token。
2. **構建驗證樹**：把這些候選 token 組織成一棵樹，每個分支是一個可能的後續路徑。
3. **一次並行驗證**：將整棵樹（例如 3 條分支，每條深度 8，共 24 個節點）包裝成一個 batch，送進 `compiled_verify_fns` 一次性計算所有節點的 logits。
4. **選擇最長接受路徑**：從根開始用模型的 logits 與樹中的 token 比對，選出最長連續匹配的那條分支，其他分支丟棄。

---

### 用具體例子說明為什麼能提高 ARL

假設我們在生成 `(15+3)×4÷2-6` 這類算術題時，模型接下來可能輸出：

- `=` (機率 0.9)
- `→` (機率 0.08)
- `:` (機率 0.02)

單路 N-gram 會押注 `=`，若模型在這裡其實想用 `→` 來表示「推導」，那單路立刻就斷了，這輪只能接受 0 個 token（如果運氣好斷在第 5 步，ARL=4）。

但 Tree Attention 會同時保持三條分岔：

- 分支 A：`= 12 → x = 6 ...` （深度 8）
- 分支 B：`→ 12 → x = 6 ...` （深度 8）
- 分支 C：`: 12 → x = 6 ...` （深度 8）

驗證時，模型會看到這三個並行的序列，並對每一個 token 進行比對。只要其中一條分支連續命中 8 步，我們這一輪的 ARL 就是 8。如果多條分支都命中很長，我們選最長的那條。

**這就是 ARL 能從 22 推到 26–28 的數學基礎**：單路在每個歧義點都有概率斷掉；多路在每個歧義點只要有一條走對，就能延續。以 80% 單步準確率計算，三條分支「至少一條連對 8 步」的概率遠高於單路，因此有效接納長度顯著提升。

---

### 為什麼能直接用到我們現有的 `_batch_replay` 基礎上？

關鍵在於我們的 `_compiled_verify[K]` 已經支援任意形狀的 token batch。現在是 `[batch_size=1, seq_len=K]`，我們只需將輸入擴展為 `[batch_size=3, seq_len=8]`（或更靈活的打包方式），在模型內部做一次並行 forward，然後在輸出端比對三條路徑的 logits 與原始 token，選出最長匹配。

`_batch_replay` 的本質是將 m 個已接受的 token 一次回放並更新 cache；我們可以把它改造成**接受最長連貫前綴 + 延伸其餘分支**的模式，計算代價幾乎不變。

## P1 — SJD-PAC 動態 K + Jakiro 多路徑生成的原理

P0 解決了「猜測多樣性」的問題，但 K 值的大小和何時展開分支還是固定的。P1 要讓系統**自己學會什麼時候該走單路，什麼時候該分岔**。

### SJD-PAC 的核心：主動草稿 + 自適應延續

SJD-PAC（Speculative Jacobi Decoding with Proactive and Adaptive Continuation）由 Snowflake 在 2026 年提出，它的兩個關鍵詞是：

- **Proactive Drafting（主動草稿）**：不等到上一輪驗證結束才生成下一輪草稿，而是在當前草稿被驗證的同時，立刻預測「哪些位置會通過驗證」，並提前生成下一輪的猜測。這在硬體上實現了「驗證與草稿的重疊」。
- **Adaptive Continuation（自適應延續）**：不是用一個固定長度 K 一直跑，而是根據當前的**不確定性（entropy）**來動態決定要預測多長。當模型對接下來的 token 非常確信（低熵），K 就可以開到 32 甚至 64；當模型猶豫不決（高熵），K 就自動縮到 4 或 8，甚至退化成單步生成。

在我們的情境中，「自適應延續」可以直接套用：如果當前生成的 token 熵值突然變高（例如從具體數字變成「因此我們可以說...」這種開放敘述），立刻將 K 縮小，防止猜測全軍覆沒。這對非數學場景的泛化至關重要。

---

### Jakiro 的思路：用混合專家同時生成不同猜測路徑

Jakiro 是 2025 年提出的方法，針對 MoE（混合專家）架構的模型（我們正好是 Mamba3-TuckerMoE！），利用**不同專家對同一輸入可能有不同預測**的特性，來生成多樣化的草稿。

原理：

- 在一次 forward 中，不只用 top-1 專家，而是同時啟動 top-2 或 top-3 專家路由。
- 每個專家給出各自的 token 預測（相當於多條草稿路徑），然後一次性送入驗證階段。
- 這個方法的好處是**無需外部草稿模型**，完全利用自身已有的專家多樣性，實現 zero-training 的多路徑生成。

結合 SJD-PAC 的自適應 K：當模型熵低時，只用單一專家，K 開大；當熵高時，同時啟用 2-3 個專家，K 適中，透過專家分歧產生多樣化猜測。

---

### 兩者組合後的工作流程

```
Step 1: 根據當前 context 計算 entropy。
Step 2: 若 entropy < threshold_1 → K=32，單路 N-gram，快速推進。
        若 threshold_1 ≤ entropy < threshold_2 → K=16，啟用 2 個專家路徑。
        若 entropy ≥ threshold_2 → K=4，啟用 3 個專家路徑，甚至退回 AR。
Step 3: 將選定的草稿（多路徑）包裝成 tree/batch，送 verify。
Step 4: 驗證並接受最長前綴，同時 SJD-PAC 的主動草稿模塊在背景預測下一輪的猜測。
Step 5: 循環。
```

這樣，我們不但能在高確定性的數學 CoT 上衝到 ARL≈28（甚至更高），也能在低確定性的開放敘述中保持穩定、不退化，從而把 3.0× 常態化。

---

## 小結

- **P0 (Tree Attention)**：靠「多路分岔 + 一次驗證」打破單路 ARL 天花板，直接從 22 推到 26–28，且與現有 `compiled_verify_fns` 完美相容。
- **P1 (SJD-PAC + Jakiro)**：讓系統根據不確定性**動態調整** K 和分支數，既放大高確定性段的收益，又保護低確定性段不失速，實現從 2.82× 到 3.0–3.2× 的跳躍。

兩階段相輔相成，P0 是 P1 的運算基礎，P1 是 P0 的智慧調度器。完成這兩步後，我們的 Jacobi 加速方案就能從「在特定題型上達標」進化為「通用推理加速引擎」。

## 二、P0 實施：Tree Attention + 多候選並行驗證

### 2.1 核心概念

將原先的**單線性猜測序列**（長度 K）改為**一棵猜測樹**。

- 樹根是 `carry_token`（上一輪最後接受的 token）。
- 在每個節點，用 N‑gram 快取提供 **top‑2 或 top‑3 的下一 token 候選**，形成多個分支。
- 整棵樹的一次驗證呼叫 `compiled_verify_fns`，batch_size = 分支數，seq_len = 每個分支的深度。
- 驗證後，從根開始沿著樹向下比對模型輸出的 argmax 與分支 token，找出一條**最長完全匹配的前綴路徑**。

**約定**：為了簡單且不使 cache 過於複雜，我們採用 **固定深度、固定分支數** 的策略：

- `num_branches = 3`（含 top-1, top-2, top-3 候選）
- `branch_depth = K // num_branches`（例如 K=32 → 深度 10，餘數可補到最後一支）
- 實際輸入形狀 `[3, depth]`，每支深度相同（不足處用 pad，但比對時忽略 padding）。

### 2.2 修改點

#### 2.2.1 在 `NGramCache` 中增加 top-k 查詢

```python
class NGramCache:
    def query_topk(self, context: tuple, k: int = 3) -> List[int]:
        """return top-k next tokens sorted by frequency or recency"""
        ...
```

如果快取中該 context 的次數少於 k，則用頻率最高的前幾個，不足的以重複最後 token 填補。

#### 2.2.2 新增 `build_guess_tree` 函數

```python
def build_guess_tree(
    carry_token: int,
    ngram_cache: NGramCache,
    context: tuple,           # 最近 n 個已接受的 token
    branch_depth: int,
    num_branches: int = 3
) -> mx.array:
    """
    返回 shape [num_branches, branch_depth] 的整數陣列。
    第 0 列全部為 carry_token（可選，視為已接受的前綴）。
    分支 i 的後續 token 由 ngram 的 top-i+1 候選及後續貪婪延伸決定。
    """
```

**步驟**：

1. 對每個分支 i（0‑based）：
   - 初始 token = carry_token
   - 下一 token 候選 = ngram 在當前 extended_context 下的 top‑(i+1) 候選。
   - 將選定的 token 加入，並繼續從 ngram 中貪婪延伸至深度滿。
2. 返回形狀 `[num_branches, branch_depth]` 的張量。

#### 2.2.3 修改驗證流程

在 `enhanced_jacobi_stream` 中，將原來「線性猜測 + 單路驗證」換成：

```python
# 1. 構造猜測樹
tree_tokens = build_guess_tree(carry_token, ngram_cache, context, branch_depth, num_branches)
# tree_tokens: [num_branches, branch_depth]

# 2. 一次性平行驗證
logits_tree = _call_verify(tree_tokens, caches, pos)
# logits_tree: [num_branches, branch_depth, vocab_size]

# 3. 沿樹尋找最長接受前綴
accepted_len, best_branch = find_longest_accepted_prefix(tree_tokens, logits_tree)
```

#### 2.2.4 實現 `find_longest_accepted_prefix`

```python
def find_longest_accepted_prefix(
    tree_tokens: mx.array,   # [B, D]
    logits: mx.array         # [B, D, V]
) -> Tuple[int, int]:
    """
    從根開始（depth=0），檢查每個分支在該深度的 token 是否與 logits 的 argmax 一致。
    遇到第一個不一致就停止，記錄各分支的最長連續匹配長度。
    回傳 (最長長度, 對應分支 index)。
    """
```

由於我們的樹根是 `carry_token`（已經在上一輪接受），所以 depth=0 必定匹配，可從 depth=1 開始比對。  
若所有分支都在深度 1 失敗，則 accepted_len=1（僅 carry_token），此時可能需要 fallback 到單步生成。

#### 2.2.5 處理接受後的回放

接受長度為 L 的前綴後，這 L 個 token（包含根）必須透過 `_batch_replay` 更新 KV/SSM cache，並且從已接受的最後一個 token 開始下一輪猜測樹。

**重要**：為了簡化實現，此時我們不保留未被接受的分支 cache。僅以最佳分支的接受前綴為準，丟棄其他分支（它們的 cache 狀態未實體化）。

#### 2.2.6 與舊配置的開關

在 `benchmark_jacobi.py` 中增加一個 config 選項 `--tree`，當啟用時使用 tree verify，否則沿用舊的線性 N‑gram。

### 2.3 預期計算成本

- 線性 K=32 時 verify 成本約為單 token 的 5.75×。
- Tree 模式：B=3, D=10（總 token 數 30），比對單 token 成本比約為 30 次 parallel forward 的實際時間，預估在 4.5–5.5×。
- 淨收益：ARL 由 22 提升至 28（+27%）遠大於驗證成本微增（甚至可能因為深度變短而更少），總吞吐量上升。

## 三、P1 實施：動態 K 與多專家路徑（SJD-PAC 簡化版）

### 3.1 動態 K（自適應延續）

利用模型輸出的 **熵（entropy）** 決定下一步的草稿長度與分支策略。

```python
def compute_entropy(logits: mx.array) -> float:
    probs = mx.softmax(logits, axis=-1)
    return -mx.sum(probs * mx.log(probs + 1e-9)).item()
```

**規則集（可調參數）**：

- `entropy < 0.5` → 高確定性區間：`K = 32`，`num_branches = 1`（單路，最快）
- `0.5 ≤ entropy < 1.5` → 中等確定性：`K = 16`，`num_branches = 2`
- `entropy ≥ 1.5` → 高不確定性：`K = 4`，`num_branches = 3`（多分支保護），甚至直接退回到單步 AR。

熵的計算可在每次接受後、生成下一輪草稿前，用最後一個已接受 token 的 logits 計算。

### 3.2 多專家生成草稿（Jakiro 啟發）

利用 Mamba3‑TuckerMoE 的專家路由資訊產生多樣化的猜測。  
具體做法（簡化版，不用修改模型結構）：

1. 在 `_call_verify` 過程中，我們可以收集不同專家對最後一層的 logit 貢獻（如果框架支援），或者更簡單：
   - 對於每個分支，我們可以微調 input embedding 或 attention mask，使不同分支的 forward 稍微“偏袒”不同的專家。
   - **更輕量的替代**：使用不同的 N‑gram 階數或不同的溫度來產生多條路徑，模擬專家分歧。

由於直接操控 MoE gate 可能侵入性太強，建議先在 P1 中實現「溫度多樣性」：讓兩條分支使用不同的溫度（如 0.0 和 0.5）從模型 logits 中採樣，得到有差異的猜測序列，再一起驗證。這也能達成 Jakiro 的多路徑效果。


```
    entropy = compute_entropy(last_logit)
```

## 四、驗證方案

### 4.1 正確性驗證（最重要）

1. **單步一致性測試**
   - 隨機取 10 條短提示，先跑 AR 基準，記錄完整輸出序列。
   - 啟用 Tree Attention（強制 B=1, depth=K）跑相同提示，比對每個 token 是否完全一致。
   - 再啟用多分支（B=3），強制只取最佳分支，比對輸出 token 流是否與 AR 一致（理論上應完全一致，因為最佳分支即 AR 的路徑）。

2. **Cache 正確性**
   - 在 `_batch_replay` 後，取最後一個 token 並執行一次單步 forward，確認輸出的 logits 與單步 AR 在相同位置的 logits 數值誤差小於 1e-4。

3. **多分支切換無殘留**
   - 交替使用不同 K 值與分支數，確保每一輪後 KV cache 尺寸正確，不出現維度錯誤。
