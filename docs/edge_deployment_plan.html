2. Tucker 的部署天然優勢

Tucker MoE 在端側部署有一個對手沒有的性質，這是整個部署方案的基石：

靜態圖友好：形狀在載入時就確定。
precompute_G_experts() 在權重載入後一次性算出 \(G = U_{\text{expert}} \otimes \mathcal{G}\)（形狀 \(E \times r_3 \times r_2\) 固定）， 以及 \(G_{\text{flat}}\)（\(r_3 \times E\cdot r_2\)）。 之後的推論只有固定形狀的矩陣乘法，沒有動態形狀——CoreML / ONNX / TFLite 的最大痛點正是動態形狀。
記憶體足跡
  • bf16：1.14 GB
  • int8：~570 MB
  • int4：~285 MB
int4 可在 iPhone 12（4 GB RAM）上舒適執行。
共享 core 的快取優勢
\(U_{\text{in}}, \mathcal{G}, U_{\text{out}}\) 三個大張量在所有 token 間完全不變—— 它們在 decode 時長駐 GPU/ANE cache， 每 token 只讀 \(U_{\text{expert}}[e]\) 的 \(r_1=4\) 行。

和主流競品的 memory-bandwidth 比較

方案每 token 需讀的 expert 權重decode 是否 memory-bound
Dense FFN（7B）全部 \(d_{\text{in}}\times d_{\text{out}}\)✅（極嚴重）
Dense MoE（Mixtral-8×7B）top-\(k\) 個 expert 全秩權重✅（仍嚴重）
Tucker MoE（本專案）只有 \(U_{\text{expert}}[e]\)（\(r_1=4\) 行）+ 預算好的 \(G_{\text{flat}}\)✗ compute-bound

4. 各平台轉換 Pipeline

4.1 iOS / iPadOS（P1，最高優先）

Tucker MoE 的靜態形狀讓 CoreML 轉換比一般 MoE 容易得多——不需要動態 expert dispatch，只有固定的矩陣乘法序列。

關鍵洞察：不要直接轉換整個前向，拆成兩段。
① prefill：用 \(G_{\text{flat}}\) 路徑（一次大矩乘），CoreML 很好轉。
② decode（B=1）：用 \(G_{\text{experts}}[e]\) 路徑（幾次小矩乘），可直接用 Metal compute shader。

步驟

  1. 在 MLX 端 export 因子：從 .npz 取出 Tucker 因子並預先算好 \(G_{\text{flat}}, G_{\text{experts}}\)，存成獨立 .npz 或 .safetensors。
  2. PyTorch 橋接：把因子載入 PyTorch（CPU float32），使用 torch.nn.Linear 組合 Tucker 的三段矩乘。
  3. CoreML 轉換（coremltools）： 
    import coremltools as ct
traced = torch.jit.trace(tucker_module, example_input)
mlmodel = ct.convert(
    traced,
    inputs=[ct.TensorType(shape=ct.Shape(shape=(1, ct.RangeDim(1,2048), 768)))],
    compute_units=ct.ComputeUnit.ALL,   # ANE + GPU + CPU
    minimum_deployment_target=ct.target.iOS17,
)
  4. Metal compute shader（decode）：SSM scan 已有 Metal kernel，Tucker decode 路徑（幾次矩乘 + gather）用 MPSGraph 或直接 Metal 寫。
  5. Swift App 封裝：MLModel + Metal command queue 整合，WebSocket interface 與現有 chat_demo.py API 相容。
ANE 限制注意。 Apple Neural Engine 不支援所有 op（如 gather、argpartition）。 Router top-k 選擇需 fallback 到 CPU/GPU；Tucker 的矩乘本體可跑在 ANE 上。 建議先量測 MLComputePlan 的 op 路由再優化。

4.2 Android — ExecuTorch（P2）

  1. PyTorch Export：用 torch.export.export() 把 Tucker forward 導出為靜態圖（因子預計算後形狀固定）。
  2. ExecuTorch 編譯： 
    from executorch.exir import to_edge
edge_prog = to_edge(exported_prog)
exec_prog = edge_prog.to_executorch(
    ExecutorchBackendConfig(passes=[QuantFusionPass()])
)
with open("tucker_moe.pte", "wb") as f:
    f.write(exec_prog.buffer)
  3. Qualcomm QNN backend：to_edge 時加 QnnPartitioner，把矩乘和 softmax 路由到 NPU。
  4. Kotlin 封裝：使用 ExecuTorch Android SDK。

4.3 Edge Linux / GGUF（P2）

llama.cpp 的 GGUF 格式支援自定義 tensor 名，Tucker 因子直接存進去：

# 自訂 GGUF 命名規則
layers.{i}.tucker.U_in        f16  [768, 256]
layers.{i}.tucker.core        f16  [4, 256, 1024]
layers.{i}.tucker.U_out       f16  [1024, 4608]
layers.{i}.tucker.U_expert    f16  [8, 4]
layers.{i}.tucker.G_flat      f16  [256, 8192]  # precomputed, 選擇性存

需要 fork llama.cpp 加入 Tucker MoE op（C++ 實作，約 200 行），利用現有 ggml_mul_mat 做矩乘即可。SSM 部分需要新的 ggml op。

4.4 Web / WebGPU（P3）

MLC-LLM / WebLLM 的 TVM relax 可自訂 op。Tucker 的三段矩乘可以表示為 TVM relay 圖，並用 tvm.tir 或 WebGPU compute shader 實作。

5. 量化策略

5.1 各平台量化建議

平台推薦精度方案預期模型大小品質損失
macOS M1/M2（16 GB） bf16 / int8 混合 現有 selective 8-bit（MoE 因子 + proj） ~570 MB ✅ 幾乎無
iOS（≥ iPhone 13，6 GB） int8 全量化 CoreML linear_quantize_weights ~570 MB ✅ 可接受
iOS（iPhone 12，4 GB） int4 Tucker 因子 對 \(\mathcal{G}, U_{\text{in}}, U_{\text{out}}\) 做 int4，\(U_{\text{expert}}\) 保 int8 ~285 MB ⚠️ 需 ablation
Android Snapdragon int4 / int8 混合 QNN 量化工具，NPU 原生 int8 ~285–570 MB ⚠️ 需 ablation
Jetson Orin int8 TensorRT 8-bit PTQ ~570 MB ✅ 可接受
RPi 5（8 GB RAM） int4 GGUF（Q4_K_M） llama.cpp 量化 ~285 MB ⚠️ 需 ablation

5.2 Tucker 因子量化的特殊考量

不要對所有因子一視同仁。 三個因子的量化敏感度不同：
因子角色量化敏感度建議
\(U_{\text{in}} \in \mathbb{R}^{768\times 256}\) 輸入投影（共享） 高：每個 token 都過 保 int8 或 bf16
\(\mathcal{G} \in \mathbb{R}^{4\times 256\times 1024}\) 核心張量（共享） 中：決定 expert 結構 int8，可嘗試 int4
\(U_{\text{out}} \in \mathbb{R}^{1024\times 4608}\) 輸出投影（共享，最大） 中：誤差被最後一層放大 int8，可嘗試 int4
\(U_{\text{expert}} \in \mathbb{R}^{8\times 4}\) Expert 係數（極小） 極高：32 個數決定 expert 選擇 保 fp32 或 bf16，絕不量化

最佳實踐：\(U_{\text{expert}}\) 保高精度，其餘因子按 int8，\(\mathcal{G}\) 和 \(U_{\text{out}}\) 可試 int4（配 perplexity 檢驗）。

8. 風險與緩解

風險說明緩解
CoreML ANE 不支援 top-k / gather Router 的 topk 選擇無法跑在 ANE Router 切到 CPU（計算量極小），Tucker 矩乘仍在 ANE；用 MLComputePlan 量測影響
SSM 狀態更新難以靜態化 Mamba 的 state carry 在 CoreML 是 recurrent state，需明確管理 用 CoreML StateType（iOS 18 新增），或 stateful buffer 手動管理
int4 Tucker 品質損失過大 特別是 \(\mathcal{G}\) 和 \(U_{\text{out}}\) 回退到 int8；或用 Activation-aware Quantization（AWQ）對重要通道補精度
Speculative decode 在 B=1 靜態圖上難以實現 SJD 需要可變長 batch verify iOS 版先不做 speculative；Android 版用 ExecuTorch 的 dynamic shape 路徑
GGUF Tucker 擴展需要 fork 維護 上游 llama.cpp 不會原生支援 Tucker 先以 ONNX 為主；GGUF 是長期方向，等社群接受後 PR
