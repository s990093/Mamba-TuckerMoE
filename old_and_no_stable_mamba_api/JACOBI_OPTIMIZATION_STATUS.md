## Bug: AR Warmup Tokens Diverge from stream_mlx.py (FIXED 2026-05-18)

### Symptom

The first 20 AR warmup tokens generated by `jacobi_stream.py` (via `enhanced_jacobi_stream`) can
diverge from what `stream_mlx.py` produces for the exact same prompt at the same temperature.
After the first divergent token the KV-cache state forks, so every subsequent token also diverges.

### Root Cause 1 — Token-0 Banning (primary)

`enhanced_jacobi_stream` bans token 0 by default (`ban_token_ids={0}`).  
The AR warmup sampler is `_safe_argmax`, which silently swaps the top-1 token with the
next-best non-banned token whenever `mx.argmax(logit_row)` returns 0.

`stream_mlx.py` uses `sample_decode_token → _advanced_sample → mx.argmax(logits)` with **no
token banning**.

Impact: When the 8-bit quantized model picks token 0 as its most-likely next token (common in
structured CoT output), the two systems choose different tokens at that step and diverge
permanently for that generation.

| Code path | Sampler | Token 0 handling |
|-----------|---------|-----------------|
| `jacobi_enhanced.py` AR warmup | `_safe_argmax` | Replaced by 2nd-best non-banned token |
| `stream_mlx.py` | `sample_decode_token` → `mx.argmax` | Token 0 emitted as-is |

### Root Cause 2 — No Stochastic Sampling in AR Warmup

`_safe_argmax` is always greedy (pure argmax). It ignores `sample_args.fast_sample`, `temp`,
`top_k`, `top_p`, and `min_p`.

`stream_mlx.py` calls `sample_decode_token` which, when `fast_sample=False` and `temp > 0`,
applies temperature + min-p + top-k + top-p + categorical sampling.

Impact: At any temperature > 0 the AR warmup tokens are always greedy while stream_mlx is
stochastic.  Correctness tests only run at `temp=0` (greedy), so this bug is hidden.

### Root Cause 3 — No Token-Count Tracking (minor, default-neutral)

`stream_mlx.py` initialises `token_counts` from the prompt and updates it after each generated
token, so repetition penalties can be applied.  AR warmup in `jacobi_enhanced.py` has no
`token_counts` and never calls `_apply_penalties_fast`.

Impact with default settings: None — default `no_penalties=True` in both files skips the
penalty path.  Impact at non-default settings (rep_pen ≠ 1, pres/freq_pen ≠ 0): divergence.

### Fix Plan

**Immediate (low-risk)**: Pass `ban_token_ids=frozenset()` to the AR warmup sampler, or bypass
`_safe_argmax` and call `sample_decode_token` directly:

```python
# In enhanced_jacobi_stream, AR warmup loop — replace:
pred = _safe_argmax(current_logit_row)

# With (requires passing sample_args + token_counts into the warmup loop):
pred_arr = sample_decode_token(current_logit_row, token_counts, sample_args)
mx.eval(pred_arr)
pred = int(pred_arr.item())
```

`token_counts` should be initialised with `_init_token_counts(prompt_ids, vocab_size)` before
the warmup loop and updated with `token_counts[pred] += 1` each step (same as stream_mlx).

**Why the ban exists**: `ban_token_ids={0}` was added to prevent `<unk>`/token-0 flooding the
`carry_draft` buffer inside the Jacobi loop, which caused runaway repetition with 8-bit models.
The fix is to keep the ban **inside the Jacobi loop only** (on `carry_draft` updates) and
**remove it from the AR warmup sampler**.

**Correctness test after fix**: Re-run `compare_ar_jacobi.py` — match rate must stay ≥ 99 %.
Also run at `temp=0.3` vs `stream_mlx.py` with `--temp 0.3 --no-fast-sample` to verify
stochastic alignment.

**Verified (2026-05-18)**:
```
K=32  warmup=5  → 80/80 tokens match (100.00%)  ✓ PASS
K=64  warmup=20 → 80/80 tokens match (100.00%)  ✓ PASS
```

## Bug 5 — tucker_einsum_fuse=True causes model to never exit `</think>` (FIXED 2026-05-18)

### Symptom

`jacobi_stream.py` generated 100-200 tokens but showed **zero visible output** for any prompt.
`stream_mlx.py` with the same prompt produced normal (if low-quality) visible text.

Debug trace (`--debug`) showed: token 0 = `\n`, token 1 = `<think>` (enters suppression),
then all subsequent tokens stayed inside `<think>` — the model never generated `</think>`.

### Root Cause

`jacobi_stream.py` had `config.tucker_einsum_fuse = True` while `stream_mlx.py` uses `False`.

The Tucker einsum fuse substitutes a custom Metal kernel that accumulates in **float32**:
```c
float sum = 0.0f;
sum += prob * x_sram[r] * float(g_sel[g_base + r * R2]);
out[b * R2 + s] = T(sum);   // downcast back to bf16
```

The standard MLX einsum path (`mx.einsum("br,bkrs->bks", ...)`) stays in **bfloat16** throughout.

At the critical **`</think>` token decision point** (token 32003), the float32 Metal path
shifts the MoE output slightly — enough to flip the argmax from `</think>` (correct) to the
next-most-likely continuation token (e.g. "Step" tid=14448). The model then generates the
entire answer inside `<think>` as a structured response (which is all hidden), and never
produces any `<final>` content.

`compare_ar_jacobi.py` was unaffected because it always had `tucker_einsum_fuse=False`.

### Fix

Set `config.tucker_einsum_fuse = False` in `jacobi_stream.py` (matching `stream_mlx.py`):
```python
config.tucker_einsum_fuse = False   # must match stream_mlx.py — Metal f32 vs bf16 shifts </think> logit
```

Also updated the corresponding `sample_args.tucker_einsum_fuse = False`.

### Verification

After fix, travel question at K=32 warmup=5:
- 200 tokens generated, all **visible** (model properly exits `</think>`)
- ARL=3.08, ngram=64%, speedup=0.46×

`compare_ar_jacobi.py` with and without system prompt: **100% match** (Jacobi still correct)

### Note on output quality

Even with the fix, the model (latest_sft_cot_model.npz) generates low-quality answers
("48-year-old society has been using a 24/7 communication system…"). This is a checkpoint
quality issue — both `stream_mlx.py` and `jacobi_stream.py` now produce equivalent garbage,
which proves they are numerically aligned. The Jacobi implementation is correct.

## Why ARL Is Low — Root Cause Analysis

The model output for "who are you":

```
<think>\n\n\n</think>\n\n</think>\n\n- | 1990s-1990s |\n- |\n- |\n- |\n...
```

Token sequence breakdown:

- Tokens 0–24: non-repetitive (`<think>`, EOS, `1990s-1990s`)
- Tokens 25–85: highly repetitive `- |\n` pattern (3-token cycle: 29899, 891, 13)
- After token 85: model hits `<|im_end|>` → if continued beyond EOS, generates non-repetitive garbage

**n-gram cache needs to SEE the `- |\n` pattern** before it can predict it.

- warmup=0: n-gram empty, ARL=4
- warmup=20: n-gram sees ~2 repetitions → ARL=8
- warmup=40: n-gram sees ~7 repetitions → ARL=19.5

**The `- |\n` pattern only starts at token ~25**, so warmup < 25 gives no repetition seeding.

## Implemented Optimizations

### 1. `_deep_copy_caches` batch eval (DONE)

- Before: N separate `mx.eval()` calls → 9.9ms
- After: ONE `mx.eval(*leaves)` batch → 3.8ms
- Impact: saves ~6ms per Jacobi round

### 2. Intermediate Mamba state extraction (DONE)

- Eliminates `_batch_replay(accepted+1 tokens, ~61ms)` for partial-accept
- Uses `forward_with_mamba_intra()` to extract hidden state at accept boundary
- Runs ONE K=1 correction step (12ms) instead
- Net saving for partial-accept rounds: ~25ms
- Overhead: +22–24ms per verify call (intra data computation)
- Adaptive dispatch: only use verify+intra when ARL EMA < K×0.9 (expecting partial-accept)
- Full-accept rounds still use regular verify (no overhead)
- Impact: 0.58× → 0.67× theoretical for ARL=8

### 3. Correctness bugs (all DONE, see JACOBI_EXPERIMENT_REPORT.md)

- Bug 1: caches_snapshot aliasing/NaN
- Bug 2: nested `mx.compile` ordering
- Bug 3: `chunk_parallel_scan_with_init` einsum head-pairing
- Bug 4: `TransformerBlock` decode attention mask inversion

## Observed Performance (2026-05-18, jacobi_stream.py, 512 tokens)

### Real-world run result

```
K=32  ngram-n=4  quant=8-bit  temp=0.0  ar-warmup=20
Rounds: 53   Accepted: 446/1693  (26.3%)   ARL: 8.42
Speed:  53.0 tok/s   Speedup: 0.65×   (AR baseline: ~82 tok/s)
```

### Root cause: ARL=8.42 < break-even threshold (ARL≥11 needed for K=32)

For K=32 to outperform AR, need ARL > verify_time/AR_time = 131ms/12ms ≈ 10.9.
ARL=8.42 is below break-even → Jacobi is slower than AR for this checkpoint.

**Model output structure for most prompts:**

- Tokens 0–25: non-repetitive (`<think>`, reasoning section)
- Tokens 25–85: repetitive pattern (ARL=15–20 achievable with warmup)
- Tokens 85+: post-EOS garbage (model ignores EOS, generates unpredictable tokens)

**Post-EOS is the killer**: with `--stop-on-eos` off, the model runs 427 garbage tokens
(out of 512 max) after natural EOS at token 85. Those 427 tokens have ARL≈3, dragging
the average to 8.42.

**Fix**: Run with `--stop-on-eos` to cut generation at EOS. Jacobi speedup for the
repetitive section alone (tokens 25–85) = 0.88× with warmup=40 (19.5 ARL).

- Before: N separate `mx.eval()` calls → 9.9ms
- After: ONE `mx.eval(*leaves)` batch → 3.8ms
- Impact: saves ~6ms per Jacobi round

### 2. Intermediate Mamba state extraction (DONE, now wired in jacobi_stream.py)

- **Now enabled in `jacobi_stream.py` by default** (`--no-dynamic-K` to disable)

## Blocking Issues for 3× Speedup

### Issue 1: Checkpoint quality (primary blocker)

The `latest_sft_cot_model.npz` generates short, low-quality responses.

- Natural EOS at token 85
- After EOS: unpredictable tokens → ARL≈3 for 85%+ of generation
- **Fix**: Run `--stop-on-eos`. Speedup for the pre-EOS section: 0.65–0.88×
- **Real fix**: Better checkpoint with coherent, longer responses

### Issue 2: Low ARL in non-repetitive sections

Non-repetitive sections (any coherent text) give ARL=3–8 at K=32.

- Break-even for K=32: ARL ≥ 11
- Only highly repetitive output (repetition rate ≥ 66%) gives speedup
- With a better model generating coherent 200+ token responses:
  - Expected ARL=15–25 → 1.5–2.5× speedup at K=64

### Issue 3: verify+intra overhead (minor)

- +22ms per verify call when using intra path
- Adaptive dispatch mitigates: only used when ARL EMA < K×0.9
- With better model, fewer partial-accept rounds → less intra overhead
